### 1a. The drain-then-remove reaper — SHIPPED, Rick-ratified

- **Anchor principle (Rick's no-push law, 2026-06-22)**: preservation is **purely local**. ### 2b. Why NOTHING we shipped can touch these — the structural gap
1. **Enumeration blindness (applies to BOTH lanes).** The reaper/janitor enumerate `git worktree list --porcelain`. A worktree whose admin registration is already gone **is not in that list**. All ~31 are past that point, so **enabling the janitor today reaps none of them.** The janitor only ever works if it runs *before* the admin entry is pruned; once `git worktree prune` (or a wholesale `.git/worktrees/` loss) happens, it goes blind.
2. **Sandbox-root confinement (extra wall on the sibling lane).** `worktree_reaper.py` defaults `sandbox_root` to `<project_root>/.claude/worktrees` and **explicitly skips any worktree whose path is `outside_sandbox`**. The 7 siblings are `projects/lupin-wt-*` — outside the sandbox — so even a list-visible sibling would be skipped by design.

**=> The prevention machinery closes the reap loop only for the narrow window while a worktree is still admin-registered AND inside `.claude/worktrees`. Outside that window — hard-killed workers, pruned admin entries, sibling-path worktrees — orphans accumulate unreaped. The 5.7 GB is the proof.**

## 3. The mechanism menu (costed) — closing the gap the 5.7 GB exposes

The reap loop is solved for the narrow in-sandbox, still-registered window. The open problem is everything outside it: *prevent creation-that-orphans* and *reap-what's-already-orphaned (incl. git-dead)*.

### Option A — Prevent-at-creation (a guard)
A `PreToolUse` guard — **same layer as the memento bypass guard** (`memento_record_guard.py`, operator gate `9e429875`) — intercepting worktree creation and **denying-unless-registered**:
- Matches `Bash(git worktree add …)` and `Agent(isolation:"worktree")` / spawn-with-worktree.
- **Denies** a worktree *outside* the sanctioned sandbox root, OR requires it to register an **owner + TTL** in the task-store — so an orphan becomes a *visible non-terminal row*, not an invisible directory.
- **Pros**: attacks root cause — a parentless/registrationless worktree can't be born. Reuses a proven guard pattern. Makes worktrees auditable; would have prevented the sibling lane entirely.
- **Cons**: `Bash` has many `git worktree add` spellings and carries arbitrary bytes (the memento §3.6 lesson — covering Bash means parsing shell). A guard is **necessary but not sufficient**. **Needs a settings.json hook install → gated on Rick**, exactly like `9e429875`.

### Option B — Reap-after-the-fact (a filesystem-anchored sweep)
Add a **second janitor sweep that is filesystem-anchored, not `git worktree list`-anchored** — the only thing that can see a git-dead orphan:
- Scan the projects parent AND `.claude/worktrees` for dirs whose `.git` is a **pointer file to a missing admin dir** (the exact broken-orphan signature). Age-gated, LOUD, never silent.
- For any orphan with recoverable work, **rescue-then-remove** (Mr Radio's blob-hash audit → auto-commit-to-branch), never blind-delete.
- **Pros**: catches precisely what Option A can't — already-stranded + git-dead. Age-based janitor **>** "delete when done" (a rule, and it WILL be forgotten — S128 thesis). This is the shape Rick already sanctioned.
- **Cons**: reactive (work sits up to the age window). Broader blast radius than the sandbox sweep — must be conservative (mandatory value-check gate). Recovering a git-dead dir's tip-SHA is genuine forensics (§2d).

### Option C — Both (defense in depth) — RECOMMENDED DIRECTION
Guard at creation (A) makes new orphans structurally hard; the filesystem janitor (B) is the backstop for what the guard can't cover and for the ~31 already on disk. Exactly the memento shape: **guard = prevention, janitor = recovery, and recovery is load-bearing because the guard has a Bash-shaped hole.**

## 4. The open fork FOR RICK (do not rule solo)

1. **prevent-at-creation (guard) vs. reap-after (janitor) vs. both?** — recommended: **both** (Option C), for the same "a guard has a Bash hole, keep a load-bearing recovery layer" reason we accepted for mementos.
2. **Guard scope**: hard-**deny** worktrees outside the sandbox root, or **allow-but-register** (owner+TTL store item)? Deny stops the bleeding; allow-but-register preserves the legitimate "sibling sandbox with repo context" use the CLAUDE.md worktree guidance relies on.
3. **Fix the enumeration blindness**: should the janitor's detection move from `git worktree list` to a **filesystem scan for the broken-orphan signature**, so it can see git-dead dirs at all? (Without this, the janitor Rick just enabled cannot clean the current 5.7 GB.)
4. **The ~31 live orphans (5.7 GB)**: authorize a value-check-then-clear pass (Mr Radio's methodology)? **Destructive + needs Rick's direct word** (blast-radius bar). Filed as store item for the recovery.
5. **Does the guard's settings.json hook ride with the memento hook** (`9e429875`)? Same install surface, same "worker touching global config" concern — likely one ruling covers both.
