# Spawn Model-Directive: Investigation + Implementation Plan

**Date**: 2026-07-02 · **Author**: María 🌸 (session 00950da2) · **Status**: RATIFIED 5/5 (Rick guided walkthrough 2026-07-02) — build HANDED to Mr Radio (lupin)
**Ask (Rick, voice)**: When a new worker is spun up, do we pass any directive to Claude Code to use a specific model, or the default? Cost-control goal: **Fable 5 for managers, Opus 4.8 for workers**. If no vehicle exists, propose one.
**Store item**: `ed84e219` (plan) · **Code surfaces**: lupin `src/lupin_mcp/cosa_voice_mcp.py`, `src/lupin_mcp/session_spawner.py`, `src/scripts/start-cc-with-tmux.sh`

## 1. Answer to the direct question

**No. Today NO model directive is passed anywhere in the spawn chain.** Every spawned worker boots as bare `claude` and inherits whatever the user-level default model is (`~/.claude` settings). Managers Rick launches interactively inherit the same default. There is no per-role, per-spawn, or per-persona model selection anywhere in the fleet today.

**However — the vehicle is ~80% pre-built.** The plumbing has an explicit pass-through seam at every layer; it was simply never threaded end-to-end:

| Layer | File:anchor | Model-directive support today |
|---|---|---|
| MCP tool `spawn_sessions` | `cosa_voice_mcp.py:2261` | ❌ No `model` param exposed to the manager |
| Orchestrator `spawn_sessions()` | `session_spawner.py:239` | ❌ No `claude_args` param; calls the builder WITHOUT it (`:363`) |
| Argv builder `build_spawn_argv()` | `session_spawner.py:154` | ✅ **Already accepts `claude_args`** and inserts them after the session name, before `--prompt` — exactly where the script wants them |
| Spawn script | `start-cc-with-tmux.sh:64,91-97` | ✅ **Already forwards** any extra positional args into the `claude` invocation, `%q`-quoted (`CLAUDE_ARGS` → `CLAUDE_CMD`) |
| Claude Code CLI | `claude --help` (verified live) | ✅ `--model <model>` — accepts alias (`fable`, `opus`) or full id (`claude-fable-5`); also `--fallback-model` |

The two missing links are (a) `session_spawner.spawn_sessions()` accepting and threading a model, and (b) the MCP tool exposing it (with a config-driven default so managers don't hardcode).

## 2. The spawn chain, as-built (verified firsthand 2026-07-02)

```mermaid
flowchart LR
    A[ "Manager session<br/>calls MCP spawn_sessions" ] --> B[ "cosa_voice_mcp.py:2261<br/>@mcp.tool wrapper" ]
    B --> C[ "session_spawner.spawn_sessions()<br/>renders brief, builds env" ]
    C --> D[ "build_spawn_argv()<br/>bash start-cc-with-tmux.sh --headless name --prompt brief" ]
    D --> E[ "start-cc-with-tmux.sh<br/>INNER = 'export PYTHONPATH...; claude &lt;args&gt; &lt;prompt&gt;'" ]
    E --> F[ "tmux new-session -e PERSONA_ENV -d INNER" ]
    F --> G[ "Child claude boots<br/>MODEL = user default (no directive)" ]
```

Key mechanics confirmed:
- **Env vs argv**: tmux does NOT inherit arbitrary parent env — the script explicitly `-e`-forwards a whitelist (`COSA_VOICE_SPAWNED_BY/HEADLESS/ROLE/PERSONA_CHAIN`, roster, governance flag). An `ANTHROPIC_MODEL`-style env route would need the same `-e` treatment. The **argv route needs zero script changes** — the pass-through already exists.
- **Role is already first-class at spawn time**: `role` (reviewer | author | observer | manager) is a spawn param, env-stamped (`COSA_VOICE_ROLE`) and templated into the brief — so a role→model policy map has a natural key already flowing through the chain.
- **Dry-run** (`--dry-run`) prints the INNER command without side effects — the natural test surface (the forwarded `--model` will be visible in the echoed command).

## 3. Recommended design (Option A — argv + INI policy map)

**Managers get Fable 5 by default posture; workers get an explicit `--model` at spawn.**

1. **Managers**: Rick launches managers himself (interactive `start-cc-with-tmux.sh` / desktop). Simplest control: the user-level default model IS Fable 5, so managers need no directive. (The script's existing extra-args pass-through already lets him pin one explicitly: `./start-cc-with-tmux.sh my-manager --model claude-fable-5`.)
2. **Workers**: every headless spawn passes an explicit `--model`, resolved: explicit MCP param → INI role map → no flag (inherit default, today's behavior — fail-open).

### INI policy map (lupin-app.ini, config-manager keys — live-retunable, mirrors the role-goals D1 pattern)

```ini
cc session spawn model manager  = claude-fable-5
cc session spawn model reviewer = claude-opus-4-8
cc session spawn model author   = claude-opus-4-8
cc session spawn model observer = claude-opus-4-8
cc session spawn model default  = claude-opus-4-8
```

Full model IDs (not aliases) for precision; aliases drift with releases. `...model default` covers unknown/new roles. An absent key → no `--model` flag → today's inherit behavior (fail-open, zero-risk rollout).

### Verification (I own; tabular results at review)

- **Unit**: argv construction with/without model; config resolution per role; unknown-role → default key; absent keys → no flag. (Extends the existing injectable-runner suite — no real tmux needed.)
- **Dry-run E2E**: `--dry-run` output shows `--model claude-opus-4-8` in the INNER command for each role.
- **Live E2E (1 spawn)**: spawn one worker with a pinned model; child self-reports its model id in the spawn-ack (the "You are powered by" line / model id is in the child's system context) → reap. Receipt = the ack line.

## 4. Alternatives considered (and why not)

- **Env-var route (`ANTHROPIC_MODEL` via `-e`)**: works, but invisible in the tmux command line (worse auditability), needs a script edit anyway for the `-e` forward, and the CLI arg is the documented first-class override. Rejected.
- **Per-session `settings.json` manipulation**: global/user-scoped, race-prone across parallel spawns, wrong altitude. Rejected.
- **Alias IDs in INI (`opus`, `fable`)**: aliases float to "latest" — a silent model upgrade could change costs/behavior under us. Full IDs; revisit if pinning becomes stale-prone.
- **`--fallback-model` rider**: worth considering as a phase-2 nicety (worker falls back to Sonnet when Opus is overloaded) — NOT in scope now; noted for the walkthrough.

## 6. Cost frame (why this matters)

All fleet children currently run the SAME (default) model regardless of role. Workers are the volume consumers (8-cap per manager, multiple managers); managers are few but judgment-critical. Splitting Fable-5-managers / Opus-4.8-workers puts the premium model exactly where judgment concentrates and the workhorse model where volume concentrates — the standard tiered-fleet cost pattern this plan enables with ~2 small diffs.
