## The predicate

A creation target is zoned `scratch` when **all four** clauses hold.

| # | clause |
|---|---|
| 1 | resolve the target and the root with `realpath` before comparing either |
| 2 | `os.path.commonpath( [ resolved, scratch_root ] ) == scratch_root` |
| 3 | `scratch_root` derives from `os.getuid()`, yielding `/tmp/claude-<uid>` |
| 4 | `relpath( resolved, scratch_root )` has **three or more** segments, and one segment matches `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$` |

A path failing any clause keeps whatever zone it has today.

### Clause 2 is load-bearing, and a string prefix is the trap

Measured against María's own probe paths:

| path | `startswith` | `commonpath` |
|---|---|---|
| `/tmp/claude-1001-evil` | `True` ❌ | `False` ✅ |
| `/tmp/claude-1001-evil/-mnt-x/<uuid>/scratchpad/wt` | `True` ❌ | `False` ✅ |
| `/tmp/claude-1001` | `True` ❌ | `False` ✅ |
| `/tmp/claude-1001/` | `True` ❌ | `False` ✅ |
| `/scratchpad/`, `/scratchpad/wt` | `False` ✅ | `False` ✅ |

A sibling directory sharing the first sixteen characters of the root is admitted by a prefix
test and rejected by `commonpath`. An admitted path then **skips registration**, which is the
orphan the guard exists to catch.

### Clause 3 is load-bearing, and `1001` is the trap

`1001` is Rick's uid on this host, confirmed by `os.getuid()`. Writing the literal is the
enumeration defect — *write the predicate the enumeration is approximating*.

### 🔴 One of the five `out` lines is not a worktree creation at all

The target of the `2026-09-17T15:49:32` line is the bare word **`whose`**. The mechanism,
read from the program rather than guessed:

`worktree_path_from_bash()` shlex-splits the command, scans for an **adjacent `worktree` `add`
token pair anywhere in the stream**, and takes the first non-flag token after it as the path.
It does not require a preceding `git`, and it does not require the pair to sit at a command
position. So **any command whose text merely contains the words "worktree add"** — prose in a
heredoc, an `echo`, a `grep` pattern, a commit message — yields whatever word follows as a
"target".

Consequences, in order of how much they matter:

1. **The `out` count is inflated by parse artifacts.** One of five in this window, and it is
   not a near-miss: `whose` is not a path by any reading.
2. **Under `LOG_ONLY` this is noise. Under enforcement it is a denial.** A command that only
   *mentions* worktree-add would be refused or forced into registration — and that phrase is
   common in precisely this line of work. Row `bd41d2fa`'s own body contains it.
3. **The scratch predicate is unaffected**: a non-path fails clause 2 and stays `out`, which is
   the right answer for the wrong reason. Arguably such a line belongs in **no** zone, because
   nothing was created — but that is a question about what the census counts, not about this
   zone.

## Whose session the uuid must belong to — ruled

**Ruling (María, 2026-09-17): the creating session's own.** A foreign uuid is not your
scratchpad; it is someone else's private tree, and writing into a tree you have not reconciled
is the precise hazard the fleet rules exist to stop.

This **overrules** the author's recommendation, which was to accept any well-formed uuid and
record a foreign one as a separate finding. The recommendation treated the question as a
taxonomy problem — one field, one claim. The ruling treats it as the *copy-does-not-merge*
hazard wearing a classifier's clothes, and that reading is the stronger one: zoning a peer's
tree `scratch` would let it skip registration **and** bless a write into a tree the writer has
not reconciled. Recorded here rather than silently replaced, so the reasoning survives.

⇒ Clause 4 gains: the matching uuid segment must be **the creating session's own**.

### The hazard that clause hides, and it is not hypothetical

Implementing "its own" requires choosing **which** id to compare against, and the harness
exposes more than one. `get_session_info()` returns a `session_id` **and** a
`stable_session_id`, the latter resolved from the process (`resolution_source: "ppid"`), and
the lupin operating rules state plainly that the stable id is *"NOT the post-/clear id or the
8-char form"* — so a post-`/clear` id exists and differs. **That statement is inherited, not
measured here.**

**If the scratchpad path keeps the pre-clear uuid while the session begins reporting a new
`session_id`, then comparing against the live id misclassifies a seat's OWN scratchpad as
foreign** — and under this ruling that demotes a legitimate scratch path to `out`, which is
the one direction the ruling exists to prevent.

#### Superseded: "compare the stable id, never the live one"

That was this document's recommendation, and **María's measurement retired it**: neither id
alone is sufficient. Recorded rather than deleted, because the reason it was wrong is the
useful part — it assumed the two ids are interchangeable views of one value, so picking the
more durable one was safe. They are not, and a seat where they agree cannot discover that.

#### Ruling (María, 2026-09-17): accept EITHER id

A path uuid qualifies when it matches **either** `claude_code.session_id` **or**
`claude_code.stable_session_id`. Accepting one and refusing the other demotes a seat's own
scratchpad to `out` in whichever case that id is the stale one.

#### 🔴 THE FIELD TO REFUSE, AND IT IS THE ONE NAMED `session_id`

`get_session_info()` returns **three** id-shaped fields, not two. Measured on this seat,
2026-09-17:

| field | value | uuid form | matches the path segment |
|---|---|---|---|
| top-level `session_id` | `ff47744c` | **no** | **never** |
| `claude_code.session_id` | `ff47744c-…-d6a3f479194c` | yes | yes |
| `claude_code.stable_session_id` | `ff47744c-…-d6a3f479194c` | yes | yes |

The top-level `session_id` is the **8-char form**. An implementation that reads the field
literally called `session_id` — the obvious thing to reach for — compares eight characters to
a thirty-six-character segment, **never matches, and demotes every scratch path to `out`**.
That failure is silent, total, and points the exact direction the own-session ruling exists to
prevent.

⇒ Compare against the two **`claude_code.*`** fields by name. Refuse a candidate that fails
the uuid form rather than letting it compare-and-miss.

⚠️ **This seat could not have found the ruling on its own**: both of its full uuids are
identical, so it cannot discriminate between them. The distinguishing case came from María's
measurement, not this one.

## The empirical question — answered

**Asked (María, 2026-09-17): after a `/clear`, does the seat's scratchpad path keep the old
uuid while the session reports a new `session_id`?**

**Answered (María, 2026-09-17): no.** A `/clear` does not leave a stale uuid in the path. It
creates a **new directory for the new live id**.

This document could not answer it. Its search found zero mismatches across 120 transcripts,
but no session in that corpus was confirmed post-`/clear`, so the instrument was never shown
returning a positive and the zero was reported as unresolved rather than as a no. The answer
came from a measurement this seat could not run.

### What her answer implies, and why it makes "accept either" provably right

The two findings compose. If a `/clear` mints a new directory for the new live id, and the
stable id is ppid-derived and survives the clear, then for a seat that has cleared once:

| directory | named for | matches live id | matches stable id |
|---|---|---|---|
| the pre-clear one, still on disk | the old live id, which **is** the stable id | no | **yes** |
| the post-clear one, in use now | the new live id | **yes** | no |

**Both directories are that seat's own.** Accepting only the live id would demote the seat's
own pre-clear scratchpad to `out`; accepting only the stable id would demote the one it is
writing to right now. Each id alone fails in one direction, and the pair covers exactly the
two directories a cleared seat legitimately owns.

⇒ The accept-either ruling is not caution about an unknown. It is the minimal rule that admits
both of a cleared seat's own trees and nothing else. **Derived here from her two findings, not
measured by this seat.**

### The 8-char field, revisited

Her note that the top-level `session_id` is **derived from the stable id** makes the case for
refusing it stronger, not weaker. After a clear, that field still derives from the *old*
(stable) id while the live directory is named for the *new* one — so a naive prefix comparison
fails too, not merely an equality check. There is no shape in which the 8-char field is a safe
candidate for this clause.
