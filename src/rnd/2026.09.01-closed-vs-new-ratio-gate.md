## 3b. Why this needed a ruling at all (the record)

Three statements were made about the threshold:

| # | as spoken | problem |
|---|---|---|
| 1 | *"If created versus closed is greater than 10 then we will allow new tickets"* | says **allow** when the list is GROWING |
| 2 | *"If it is less than 0 which would indicate that the list is growing then new tickets are denied"* | a **ratio cannot be negative** |
| 3 | *"Success if under 1.0 and failure and why"* | says **deny** when the list is growing |

**(1) and (3) point in opposite directions, and (2) names a value the stated measure cannot take.**
All three are consistent with the *intent* in §2; none of them can be implemented as literally spoken.

### Two coherent readings

**Reading A — RATIO.** `created ÷ closed`

| value | meaning | gate |
|---|---|---|
| `< 1.0` | closing faster than creating — list shrinking | **allow** |
| `≥ 1.0` | creating at least as fast as closing | **deny** |

Matches statement 3 exactly, including the 1.0 boundary. Cannot go negative, so statement 2
does not fit it.

**Reading B — DELTA.** `closed − created`

| value | meaning | gate |
|---|---|---|
| `≥ 0` | list flat or shrinking | **allow** |
| `< 0` | list growing | **deny** |

Matches statement 2 exactly, including the negative value and the words *"the list is growing."*
It is not a ratio, so statement 3 does not fit it.

⇒ **Both encode the same intent.** They differ only in what number appears in the bar.

**Recommendation: take A for the GATE and display BOTH in the bar.** Rick said "ratio" and
"1.0" twice, so the gate arithmetic should be the ratio — but the delta is the number a human
actually reads at a glance (*"we are seven rows deeper than yesterday"* beats *"1.4"*).
Showing both costs nothing and removes the ambiguity permanently.

## 4. Edge cases nobody has ruled on

| case | why it matters | proposal |
|---|---|---|
| `closed = 0`, `created > 0` | **division by zero**, and it is the COMMON case on a quiet day | **deny** — a window where nothing was finished is exactly what the gate is for |
| `closed = 0`, `created = 0` | `0/0` — nothing happened at all | **allow**, and display `—` rather than a number. An idle window is not a failing window |
| very small windows | 1 closed / 2 created reads as ratio 2.0 and looks alarming on almost no data | display the raw counts beside the ratio, never the ratio alone |

## 5. 🔴 What counts as "closed" — the loophole that decides whether this works at all

**If `dropped` counts as closed, the gate is trivially defeated**: drop three stale rows, mint
three new ones, ratio stays 1.0 forever and the list never shrinks. That is the exact asymmetry
Rick filed this against, wearing a green light.

**Proposal: `done` only.** `dropped` is excluded from the numerator.

⚠️ **The cost of that choice, stated rather than hidden**: legitimately dropping dead rows then
earns no credit, which mildly discourages board hygiene. Accepted deliberately — the alternative
is a gate that can be satisfied by deleting the evidence.

### 11.2 🔴 A clean board prints a BARE NUMBER — the requested format assumes a label that is not always there

`_formatTaskListCount` documents this deliberately:

> *"ZERO PARKED PRINTS THE BARE NUMBER. A clean board says `3`, not `Live: 3 · Parked: 0 ·
> Total: 3` — the split is a disclosure that only earns its space when there is something to
> disclose."*

So today's header on a clean board reads `📋 Task List: 3`, **not** `Live: 3`. The requested
string — `Task List · Live: 25 · Closed vs New Ratio (24hrs): ____` — assumes `Live:` is always
present.

**This is a real fork, not a detail** (see Q6): either `Live:` becomes unconditional, which
overturns a deliberate design decision with its rationale written into the docstring, or the ratio
appends independently and a clean board reads `Task List · 3 · Closed vs New Ratio (24hrs): 0.40`.

### 11.3 The counts — the API can answer this, with one cap that matters

`GET /api/tasks/events` already exists and takes exactly the filters this needs:

```
actor · transition · project · since · until · limit · offset
```

⇒ **The "closed" side is a `transition` + `since` query.** No new storage, no migration.

🔴 **But `limit` is hard-capped at 500** (`Query( default=100, ge=0, le=500 )`), and the endpoint
returns `count = len( rows )` — **the length of the PAGE, not the size of the match.** A caller
that asks for a 24-hour count and reads `count` gets a number that is correct until it silently
is not, with nothing in the response saying so.

**This is the shape this fleet keeps getting bitten by**: a number that reads as authoritative and
caps out without complaining. The ratio must be computed from a **real count** — a dedicated
count query, or a server-side aggregate — never by paging `/tasks/events` and measuring the page.

### 11.3b ✅ SETTLED — creation DOES emit an event, and both halves live in one table

`postgres_models.py` (`class TaskEvent`) documents it outright:

> *"transition: `from->to` string (creation stamps `->queued`)"*

and the repository confirms the stamp is BUILT, not hardcoded — `task_repository.py` appends
`f"->{status}"` at creation. **So a creation event is any transition with an EMPTY left side**, and
a closure is any transition whose right side is `done`. Both halves come from one table, one query
shape, no migration.

### 11.4 🔴 …BUT THE EXISTING ENDPOINT CANNOT ASK EITHER QUESTION

`query_events`' own contract states the limit plainly:

> *"each filter is None (no constraint) or an **exact-match** value"*

| the ratio needs | the filter can express |
|---|---|
| every creation → transition **starts with** `->` | ❌ exact match only |
| every closure → transition **ends with** `->done` | ❌ exact match only |

⇒ **Neither half is expressible.** Closures arrive as `queued->done`, `in_progress->done`,
`review->done`, `blocked->done` — several distinct strings, and an exact-match filter would have to
enumerate them. **An enumeration is a list somebody has to keep current**, which is the same rot
this fleet has been repairing all week: add a status, and the closure count silently undercounts
with nothing failing.

Creation is worse: the stamp is `f"->{status}"`, so it varies with whatever initial status the
caller passed. **A hardcoded `->queued` filter would miss every row created blocked or parked.**

⚠️ **Compounding it — `count` is the PAGE, not the match.** `limit` is capped at 500
(`Query( default=100, ge=0, le=500 )`) and the endpoint returns `count = len( rows )`. A caller
asking for a 24-hour figure gets a number that is right until it quietly is not, with nothing in
the response saying so. **That is the failure shape this fleet keeps finding: a reading that looks
authoritative and caps out without complaining.**

### 11.5 What the build actually needs

**Not** a frontend that pages the event stream and counts what came back. It needs a **server-side
aggregate** — one endpoint returning `{ created, closed, ratio, window_hours }` computed in SQL:

- **created** = transition `LIKE '->%'` (an empty left side), never an enumerated status list
- **closed** = transition `LIKE '%->done'`, with `dropped` excluded per Rick's ruling
- both bounded by `ts >= now() - 24 hours`

⇒ **That aggregate is the real unit of work here, and it is server-side.** The bar and the gate are
both thin consumers of that one number — which also means they cannot disagree with each other.

### 11.4 What this changes about the estimate

The bar is small and well-isolated. **The counts are where the work is**, and the honest sequence is:

1. Settle whether creation emits an event (one grep, by someone in that tree).
2. Add a real count — not a paged length.
3. Then the bar, then the gate.

### The window

| | count |
|---|---|
| **created** | **10** |
| **closed (`done`)** | **11** |
| dropped — excluded per the ruling | 1 |
| **ratio `created ÷ closed`** | **0.91** |
| **gate verdict** | ✅ **ALLOW** (below 1.0) |

⇒ **The fleet is currently just under the line** — closing very slightly faster than it files.
A useful place to start a warn-only week: the gate would not be firing today, so the first thing
it reports will be real drift rather than a backlog of noise.

### 🔴 The design claims are no longer arguments — they are measured

**1. Creation stamps are NOT uniform.** Measured distribution:

```
->queued    8
->blocked   2
```

⇒ **A hardcoded `->queued` filter would have missed 2 of 10 creations — a 20% undercount**, and it
would have undercounted *silently*, reporting a healthier ratio than the truth. This was written up
in §11.4 as a reasoned hazard; it is now an observed one, on one ordinary day.

**2. Closure stamps are already three distinct strings.**

```
blocked->done       4
in_progress->done   6
queued->done        1
```

⇒ An exact-match enumeration needs all three **today**. `review->done` and `parked->done` are both
reachable states that simply did not occur in this window — so the enumeration is already incomplete
and nothing would say so. **This is why §11.5 specifies a `LIKE '%->done'` suffix match rather than
a status list.**

**3. Excluding `dropped` moves the number.** With dropped counted as closed the ratio would read
`10 ÷ 12 = 0.83` instead of `0.91`. One row, and it moves the figure by 0.08 on a quiet day — so on
a day when somebody clears a dozen dead rows, the difference between the two rulings is the
difference between a gate that holds and a gate that opens.

### ⚠️ What this measurement does NOT establish

- **One quiet day is not a distribution.** 109 events, 10 creations. Nothing here says what a busy
  day looks like, and the 500-row page cap **was not exercised** — so §11.4's cap hazard remains
  un-refuted rather than confirmed harmless.
- **The window is a rolling 24h taken once.** No trend, no variance, no idea whether 0.91 is typical
  or a good day.
- ⇒ **This is exactly what the warn-only week is for.** Do not tune the 1.0 threshold on this
  single reading.

## 13. NEW REQUIREMENT — the threshold becomes an operator slider

**Rick, 2026-09-01 by voice**, after the six rulings above.

> *"Make it a slider that runs in 0.1 increments, just like the TTS slider only in tenths, not
> eighths. Default will currently be 1.0 as set within the configuration manager's ini file. The
> slider value changes created within the notifications client will be propagated to the ini file
> such that every time the task list is updated it pulls that value from the configuration
> manager's contents."*

**The purpose, in his words** — and it changes how the gate should be understood:

> *"at the end of a sprint I will successively drive the new ticket ratio downwards, so we
> basically only see tickets left to complete the sprint and that no new ones are added."*

⇒ **The threshold is not a constant to be tuned once. It is a sprint instrument.** 1.0 is the
steady-state setting; the operator walks it down toward zero as a sprint closes, tightening the
tap. That reframes §7's warn-only ramp as the *starting* position of a dial rather than a one-off
decision.

### 13.1 The dial, and what its ends mean

| setting | behaviour |
|---|---|
| **1.0** (default) | allow while the fleet closes at least as fast as it files |
| 0.5 | allow only while closing **twice** as fast as filing |
| **0.0** | **hard freeze** — no ratio can be below zero, so every new ticket is refused |

⇒ **`0.0` is a total moratorium with no special-casing.** The dial's own bottom stop *is* the
moratorium Rick declared by voice this morning — the mechanism replaces the instruction exactly,
which was the point of §2.

### 13.2 🔴 "Just like the TTS slider" describes the WIDGET, not the plumbing

The TTS slider is the right visual model — same control, `step` changed from `12.5` to `0.1`. But
its **persistence is entirely different**, and the difference is the whole build:

| | TTS slider (today) | ratio threshold (asked for) |
|---|---|---|
| where the value lives | **`localStorage`** — this browser only | **the INI** — one value, whole fleet |
| what the INI does | **seeds a default** on first load | **holds the live value** |
| direction of flow | INI → browser, one way | **browser → INI**, write-back |
| who it affects | the viewer looking at the page | **every seat that tries to file a ticket** |

Verified in source: `notifications.js` `setupEventListeners()` — the TTS handler ends at
`localStorage.setItem( this.TTS_FRACTION_PREF_KEY, ... )`. **It never writes server-side.**

⇒ **There is no browser-to-INI write path in this codebase today.** That is new machinery, and it
is the actual work in this requirement — the widget is the easy half.

⇒ **And `localStorage` would be wrong here, not merely different.** The gate runs server-side on
the create path; a value living in one operator's browser cannot gate anything. Rick asked for INI
persistence and that is the correct call, not a preference.

### 13.3 ✅ The reload method exists

`ConfigurationManager.init( config_block_id, config_path, splainer_path, silent, debug, verbose,
cli_args )` — `src/cosa/config/configuration_manager.py:204`. Rick's *"init method for the
ConfigurationManager singleton that allows for dynamic reloading"* is real and confirmed, not
assumed.

### 13.4 ⚠️ ONE CONSEQUENCE TO FLAG — the INI is version-controlled

`git ls-files` confirms `src/conf/lupin-app.ini` is **tracked**. So a slider drag writes to a file
git watches, which means:

- Every threshold change shows as a **modified tracked file** in `git status`, for every session.
- The bounce script's dirty-tree warning will name it, every time, in the broadcast to the fleet.
- A bounce **serves whatever is in the tree**, so an un-committed slider position ships on the next
  restart — which is fine here (it is the intended live value) but is the same mechanism that makes
  an accidental edit ship.
- Two operators dragging the slider produce **competing writes to a tracked config file** with no
  merge story.

**This does not block the requirement, and I am building to it as asked.** Flagging it because
"an operator drags a slider and a version-controlled file changes underneath the fleet" is a
property somebody should have chosen on purpose rather than discovered later.

**The alternative, if it ever bites**: keep the INI as the *seed default* (its current job for TTS)
and hold the live value in an untracked runtime override the ConfigurationManager reads after the
INI. Same slider, same reload, no repo churn. **Not proposed as a change — recorded so the option
is on the record.**

### 14.1 Scope correction to §12, taken from Mr Radio and correct

§12 says a hardcoded `->queued` filter *"undercounts by 20%"*. **That is 20% of MY 24-hour window,
not a rate.** Board-wide the same measure is **4 of 2,296 = 0.17%**. Both figures are true about
different populations, and neither is "the" rate — it depends entirely on how many rows were minted
`blocked` in whatever window you look at.

**The argument is unaffected** — a filter that silently misses a whole creation lane is wrong at any
rate — but the number needed its population named, which is the same discipline this epic has been
enforcing all week. Both figures now live in his test so nobody quotes one as the other.

### 14.2 The suffix-match argument got a better proof than mine

§11.4 argued against an enumerated status list from the shape of the code. Mr Radio's measurement
is stronger: **`review->done` and `parked->done` are both real on the board and both absent from
the 24-hour window.** So an enumeration written from a day's observation would have been incomplete
the moment it shipped, and nothing would have said so. He used a `LIKE` suffix match.
