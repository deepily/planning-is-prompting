## 1. What Rick asked for, in his own terms

> Chop the display string down from `Closed vs New Ratio (24hrs): 0.25` to **`Gate: 25%`**, with a
> hover that shows the full description `Closed vs New Ratio (24hrs): 25%`. The ratio is multiplied
> by 100 and formatted as a percentage; **going above 100%, up to 200%, is fine**. Shortening the
> string **makes room for the slider**. The percentage is **green when the gate is open** to new
> tickets and **red when it is closed**, so the state is readable at a glance. When the slider
> changes the threshold, **the colour updates automatically to preview the effect** over the same
> 24-hour window.

**The intent, in one line, because it drives every trade-off below**: *overload a small horizontal
space so it carries more information than it did before* — not merely make it shorter.

## 2. The display

| state | bar shows | colour |
|---|---|---|
| gate **open** (ratio **<** threshold) | `Gate: 25%` | **green** |
| gate **closed** (ratio **≥** threshold) | `Gate: 140%` | **red** |
| idle window — `closed = 0, created = 0` | `Gate: —` | **green** (§4 of the parent: an idle window is not a failing window, and it **allows**) |
| `closed = 0, created > 0` | `Gate: ∞` *(see Q3)* | **red** (§4: **deny** — a window where nothing was finished is exactly what the gate is for) |

**Hover** carries the long form: `Closed vs New Ratio (24hrs): 25%`.

**Percentage conversion**: `displayed = round( ratio × 100 )`. Ratio stays `created ÷ closed` per the
parent's ruling; only the *rendering* changes. Values above 100% are expected and legal.

## 3. The colour rule, stated so it cannot drift

> **green ⇔ the gate would ADMIT a new ticket right now. red ⇔ it would REFUSE one.**

Not "low is green". Tie it to the **verdict the gate would actually return**, so the colour can never
disagree with the behaviour. If the comparison changes later, the colour follows for free.

⇒ **Threshold is the boundary and the comparison is strict**: `allow ⇔ ratio < threshold`. At exactly
the threshold the gate **refuses**, so exactly-at reads **red**. Worth stating because `100%` on a
`100%` threshold is the case a reader will most often see and most easily guess wrong.

## 4. The slider preview — what moves and what does not

When the operator drags the threshold slider, **the number does not change**. The ratio is a
measurement of the last 24 hours; the slider changes only the line it is compared against. **What
changes is the colour**, at the moment the slider crosses the current ratio.

That is exactly the value Rick is asking for: *the colour is a live answer to "what would this
setting do to me right now?"*, without the operator computing anything.

🔴 **A PREVIEW MUST NOT BE MISTAKEN FOR STATE.** While the slider is uncommitted, the colour shown is
a **hypothetical**. If it renders identically to the committed state, an operator who drags, is
interrupted, and glances back reads a setting that is not in force as though it were.
**Recommendation**: render the uncommitted preview visually distinct — a dashed underline or reduced
opacity on the percentage — reverting to solid the moment the value is saved. Cheap, and it is the
difference between a preview and a lie.

## 5. 🔴 Conflict with the parent doc — surfaced, not resolved

The parent's §4 says, for small windows:

> *"display the raw counts beside the ratio, **never the ratio alone**"* — because `1 closed / 2
> created` reads as `200%` and looks alarming on almost no data.

**This request removes the counts from the bar.** The two are in direct tension, and the tension is
real rather than pedantic: `200%` in red on two tickets is the single most likely way this display
misleads its reader.

**Recommendation, which satisfies both**: put the **raw counts in the hover**, so the bar stays short
and the disambiguating data is one gesture away —

    Closed vs New Ratio (24hrs): 25%   ·   5 created / 19 closed

That §4 line is a **proposal, not one of the eight rulings**, so this is Rick's to overrule cheaply.
But it should be overruled deliberately, not by silence.

## 6. Open questions for Rick

| # | question | recommendation |
|---|---|---|
| **Q1** | Does the **slider read in the same units**? A bar showing `25%` beside a slider reading `1.0` asks the operator to compare two units in their head. | **Yes — render the slider `0–200%`, step `10%`.** Same underlying `0.0–2.0` step `0.1` value; display only. One unit on screen. |
| **Q2** | Do the **raw counts move to the hover** (§5)? | **Yes.** Keeps the bar short and answers the `200%`-on-two-tickets problem. |
| **Q3** | What does `closed = 0, created > 0` render as? It is a **deny**, and it is the common case on a quiet day. | **`Gate: ∞`, red.** Honest, unmistakable, and one character. `999%` would be a lie with a number's authority. |
| **Q4** | Is **green/red alone** enough? Roughly 1 in 12 men has a red/green deficiency, and this is a shared screen. | **Add a glyph** — `▲`/`▼`, or `Gate ✓ 25%` / `Gate ✕ 140%`. Costs one character in the space we are trying to save, which is why it is a question and not a recommendation I would just take. |
| **Q5** | Should the label be **`Gate:`**? It reads naturally as *"the gate is 25% open"*, which is not what the number means. | **Keep `Gate:`.** It is short, the colour carries the actual state, and the hover disambiguates. Flagged only so the choice is deliberate. |

## 7. What this does NOT change

The ratio's definition, window, `done`-only numerator, P0 and `cc-task:` exemptions, warn-only ramp,
silent-on-success, and the `Live:` count — **all unchanged**. This is a rendering and interaction
change over the same number. Anything here that appears to move one of the eight rulings is a
mistake in this document, not a new decision.

## 7.5 🔴 MEASURED — the constraint is a WIDTH BUDGET, not "make it shorter"

Krishna 🦚 measured this on the real header, 2026-09-01, after this doc was written. **It supersedes
§8's "not measured" on the sizing question**, and it is sharper than anything the brief assumed.

> **The true statement is: compacting the clause to ABOUT 107px lets the slider fit.**

| fact | value |
|---|---|
| slider width | **140px, fixed** |
| header slack as-is | **~⅕ of the slider** — so the slider cannot simply be ADDED |
| **budget for the clause** | **≈107px** |
| shortened candidates tried | **4** |
| candidates that fit without wrapping | **1 — `Gate: 25%`** |

**Two corrections this forces on the record:**

1. ⚠️ **The runner-up was BELIEVED to fit and actually WRAPS** once the slider's own label and the
   gap are counted. A near-miss nobody writes down is one the next person repeats.
2. ⚠️ **I told Rick "shortening does not buy you the slider."** That was my inference over Krishna's
   first figure, and it does not follow — shortening is *precisely* what frees the room. Retracted
   to him directly. His brief was right on both counts.

**🔴 FITS IS NOT LOOKS RIGHT.** Krishna reports a **collision / overlap** at the fitting width and
sent Rick a **render rather than a verdict**. That instinct is worth more than the measurement: an
overlap is something you SEE and cannot compute. **Nothing here is a claim that the result looks
acceptable** — only that it does not wrap.

### What the budget means for everything downstream

**≈107px is now a standing constraint on this clause, not a one-off.** Any future label — a longer
word, a glyph, a second figure — must be priced against it before it is proposed.

⇒ **This directly threatens Q4 (the accessibility glyph).** `Gate ✓ 25%` is wider than `Gate: 25%`.
If the glyph does not fit inside 107px, then Q4 is not a value call about clutter at all — it is a
question of what ELSE leaves the header to pay for it, which is a different and larger question.
**Priced with Krishna before Rick is asked to rule on it**, so he is not choosing blind.

### Q4 priced — the glyph is affordable, and the header is now effectively FULL

Krishna measured the widest legal string **with the glyph and with the slider in place**: it fits.

⇒ **Q4 stays what §6 framed it as** — a small value call about clutter, not a question of what else
leaves the header. Rick is not choosing blind.

🔴 **BUT THE MARGIN IS THIN: 13–35px of headroom.** That is the whole remaining budget for this
header, glyph included.

⇒ **Treat the header as FULL from here.** Anything added later — a second figure, a longer word, an
icon, a badge — **must be re-measured before it is proposed**, not estimated. A 13px margin is not a
margin you reason about; it is one you measure against. This is the number to quote at the next
person who wants to put something in that bar.
