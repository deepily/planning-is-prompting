# Should the cosa-voice MCP server be split? — evaluation

**Author**: María 🌸, 2026-10-01 · **Status**: evaluation only, no lupin code touched · **For**: Rick

**Asked for** (Rick, voice, 2026-10-01): *"review the contents of the current MCP adapter to see if it needs to be refactored and broken into 2 or 3 separate MCP services that are semantically grouped. I know it's grown a lot in an ad hoc manner."*

## 1. Verdict

1. **Refactor it: yes. Split it into separate services: not yet, and not into three.** The file has outgrown one module, but almost everything in it leans on one shared block of session-identity code, so separate processes would each need a copy of that block or a new shared library first.
2. **One group is cleanly separable today: the four code-lookup tools.** They share nothing with the rest except the server object. If anything becomes its own service, it is that group, and the trigger is how long a live lookup takes once Jev is switched on.
3. **The size problem is mostly words, not code.** The tool descriptions run to about 87,000 characters and the ten task tools hold 43% of that. Trimming descriptions is cheaper than any split and helps every seat.

⚠️ **This reopens your own ruling of 2026-09-30**, the day before: *"the reuse tools merge into the existing cosa-voice server … No second server or installer"* (lupin plan 2, line 113). Option C below is the opposite of that. It is listed because you asked for the evaluation; the recommendation keeps your ruling in force for now.

## 3. What ties the groups together

| Shared thing | Who needs it |
|---|---|
| **Session identity boot**: project detection, session id, sender id, the bridge-file watcher, the refusal to act under a borrowed identity. About 845 lines at the top of the main file | 27 of 37 tools: every group except code lookup |
| Persona lookup | commons, DM, task writes, spawn |
| Outbound API key | DM, task, spawn (already its own module) |
| Liveness stamp on every call | all 37 (already its own module) |
| Start-up side effects: account login check, bridge-watch thread, commons archival thread | once per process today; **once per service if split** |
| ✔ Fleet calls voice in-process: self-respin imports `ask_yes_no` from the server module | fleet → voice |
| ✔ Fleet calls DM in-process: the reap imports the DM sender from the server module | fleet → DM |
| Fleet reads task events and posts notifications directly | fleet → task, fleet → voice |

⇒ **Fleet cannot leave voice and DM without those calls becoming cross-process**, and **nothing but code lookup can leave without the identity boot coming along**.

## 4. What a split would and would not fix

| Hoped-for gain | Does a process split deliver it? |
|---|---|
| A slow or blocking call no longer freezes the others | **Partly, and mostly already fixed.** ✔ The code documents the defect: one process per seat, and a blocking ask used to stall everything for up to 610 seconds. Nine tools now run off the main loop. `dismiss_sessions` does not, and can hold the loop for a whole reap. Offloading it is a one-line change; a split is not needed for it |
| Fewer tokens per seat | **No.** The description text moves, it does not shrink. Trimming it does. *Estimate, not a measurement:* at roughly four characters per token the descriptions are on the order of 22,000 tokens and the start-up instructions about 6,000. How much each seat actually pays depends on whether tools load on demand, which I did not measure |
| A bug in one group cannot take down voice | **Already handled** for the newest groups by importing them lazily inside each wrapper |
| A fix reaches seats without a restart | **No.** Each service is still a child of the seat. Whether one service can be restarted alone inside a running seat is unverified |
| Seats only see the tools their role needs | **Yes, but a split is the expensive way.** One server can register groups by role from an environment variable at start-up |
| The file becomes maintainable | **Yes, but that is a module refactor**, not a service split |

**What a split costs, whichever line is drawn**

- **Every tool that moves changes its full name.** Tool names carry the server's name, so every document, hook and allow-list that names a moved tool has to change. Counted 2026-10-01 with `git grep` for the full-name prefix in tracked files:

  | Repository | References | Files |
  |---|---|---|
  | lupin | 175 | 55 |
  | planning-is-prompting | 22 | 8 |
  | lupin-mobile | 10 | 5 |

  Most are voice tools: `notify` 76, `ask_yes_no` 34, `converse` 20, `ask_multiple_choice` 17, the DM sender 11. **The four lookup tools are named nowhere (0 references)**, so option C renames nothing that anyone cites. Option D would move the DM, commons, task and fleet tools: a few dozen references. The voice tools stay put under every option. Not counted: untracked files, other machines, and references that use the short name without the prefix.
- **N processes per seat instead of one**, each repeating the login check and its threads, across a fleet of twelve.
- **A second installer and config entry**, which your 2026-09-30 ruling specifically avoided.
- **The identity boot extracted into a shared library first**, with its 107 tests re-homed.

## 5. Options

| | Option | What changes | For | Against |
|---|---|---|---|---|
| **A** | **Refactor inside one service** *(recommended)* | Break the 5,838-line file into one registration module per group; lift the identity boot into its own module; trim the task-tool descriptions; fix the stale counts; offload `dismiss_sessions`; add start-up instructions for the three groups that have none | No tool is renamed, no installer changes, no seat config changes. Removes the maintainability problem and most of the text weight. Makes any later split a small step | Does not isolate processes. A large diff in a file 21 test files import whole |
| **B** | A, plus role-based mounting | Seats declare a role; workers do not get fleet tools, reviewers get lookup tools | The semantic grouping you asked for, at the surface the seat sees, with one process | A seat promoted mid-session needs a restart to gain tools |
| **C** | A, then carve out code lookup as a second service | The four lookup tools move to their own server | The only seam with no shared state. Lookup has different needs: a 32-thread sweep, toolchains (node, dart) that lupin's plan says are not on the voice server's path, and calls that may take minutes. Nothing cites these four tools by full name yet, so the rename is free today and gets dearer once the reuse rule is written into workflows | Reverses your 2026-09-30 ruling. A second installer. The call log currently borrows the session identity |
| **D** | Three services: voice and session · coordination (commons, DM, task) · fleet | Full split along the groups | Cleanest on paper | Fleet's in-process calls into voice and DM become cross-process. About 30 tools renamed. Identity boot in three places. Highest cost, and the blocking problem it would solve is already mostly solved |

## 6. Recommendation

1. **Do A now.** It is the part that is certainly worth doing and it is the prerequisite for everything else.
2. **Do B with it if you want seats to see fewer tools.** Decide this one on taste: it changes what a seat can do, not just how the code is laid out.
3. **Hold C until one number exists**: how long a live `check_exists` takes once the Jev sweep is switched on. If a lookup runs for minutes inside the voice process, carve it out; if it runs in seconds, your 2026-09-30 ruling stands on its merits.
4. **Do not do D.**

The build belongs to a lupin-resident crew. Nothing here should start without your ruling.
