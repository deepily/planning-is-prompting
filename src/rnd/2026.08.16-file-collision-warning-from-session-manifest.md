# Stopping two sessions editing the same file — a warning built from the manifest

**Date**: 2026-08-16
**Authors**: María 🌸 (`11aa861f`) and Mr Radio 🦉 (`927fa30a`)
**Status**: design, for review then implementation
**Requested by**: Rick, 2026-08-16 — *"it would be good to know … which ones are open and by who … don't we already have that in the manifest?"*

---

## 0. The answer to Rick's question

**We have the data shape. We do not have the thing that prevents a collision.**

`.claude-session.md` is a **staging ledger, not a lock table**. It records what *you* touched so
*you* can stage it at commit time. Preventing a collision needs the opposite of all four properties:

| the manifest today | what a collision check needs |
|---|---|
| records what you touched, **after** the edit | knows who has it open, **before** the edit |
| keyed by **session** | keyed by **file** |
| read at commit time, **by its author** | read at edit time, **by whoever is about to write** |
| depends on remembering after every edit | fires whether or not anyone remembers |

## 1. What actually happened today

María had an uncommitted 37-file rename sweep in the lupin working tree — including
`src/cosa/rest/v2/registry.py` — when Rachel put Sam on the generator row, whose first step edits
that same file. **Nothing in the system caught it.** It was caught because Rachel sent a DM asking,
by hand, before her crew got deep. **We cannot staff that.**

**The tell**: both authors found the overlap by reading a **git diff**. Neither consulted the
manifest, and the manifest would not have helped if they had.

## 3. The design — one warning, three signals

A **`PreToolUse` check on `Edit` and `Write`** that resolves the target path and prints, before the
edit lands:

```
⚠️  Tiffany 💍 (563baeb3) has been live in src/cosa/rest/v2/registry.py — last activity 4 min ago.
```

Each signal fixes a different failure, and **none is sufficient alone**:

| signal | contributes | failure if omitted |
|---|---|---|
| **`PostToolUse` recording hook** — append `(session, file, ts)` on every Edit/Write | entries exist **without anyone remembering** | the manifest is empty exactly when it matters — today's case |
| **join against the live roster** *(Mr Radio)* — a section whose session is not in the observed list is dead, whatever it claims | only genuinely-live sessions warn | 19 stale contests; readers learn to scroll past |
| **git dirty-state** | catches the file **nobody recorded** | a confident, wrong all-clear |

### 3.1 Three states, not two

| state | render |
|---|---|
| a **live session** claims the file | ⚠️ warn, naming persona **and** session hash |
| **nobody** claims it, working tree **clean** | silent — the only true all-clear |
| **nobody** claims it, working tree **DIRTY** | ⚠️ *"uncommitted changes here and no live claimant — someone unrecorded is working in this file"* |

🔴 **The third state must never render as an all-clear.** Mr Radio's framing: *a join-only design is
worse than the status quo, because "nobody is here" on an unrecorded file looks authoritative.*
Today it would have said exactly that about `registry.py` while two crews were in it.

**And it is the only signal that depends on nobody having done anything right.** Git's working tree
is ground truth — a dirty file is dirty whether or not a single seat ever wrote a manifest line.
That is why it ships **first** (§7): it covers the whole adoption gap, when most sessions still
record nothing. `registry.py` tonight is dirty and unclaimed, and would warn correctly **before any
hook exists**.

### 3.2 Warn — never block

A blocking check gets disabled the first Friday it is wrong, and then protects nothing. Name the
persona **and** the 8-char session hash, so the reader can DM them in one step instead of hunting.

### 3.3 Why not just use git

`git status` knows a file is dirty. **It cannot tell you which session.** That is the manifest's one
irreplaceable contribution, and it covers exactly the uncommitted window where the hazard lives —
once work is committed, git handles conflicts itself.

## 4. What this will not do

1. **It is not a lock.** Two sessions can still edit the same file; they will simply know.
2. **It does not cross a machine boundary.** `.claude-session.md` is git-ignored and local.
3. **It cannot see work outside the harness** — a hand edit in an editor records nothing. The
   dirty-state signal is what partially covers that.
4. **It does not replace asking.** Rachel's DM remains the gold standard; this makes the *default*
   safe when nobody thinks to ask.

---

## 5. Open questions for review

1. **Where does the index live?** Invert `.claude-session.md` in place, or maintain a derived
   `by-file` index? A derived index is cheaper to query and can be rebuilt from the sections.
2. **What counts as live** — the arbiter's roster, or the tmux session list? **Recommend the roster,
   falling back to tmux when `:7999` is down**; a warning that silently stops working during a
   bounce is the exact failure this design exists to prevent.
3. **How stale is stale *within* a live session?** A session live six hours may have finished with a
   file an hour ago. Recommend surfacing last-activity-on-that-file rather than filtering on it.
4. **Repo scope.** A session working in two repos (this one did) needs a section in each. Should the
   recording hook auto-register on first edit in any repo?
5. **Cost.** `PreToolUse` runs on every edit. It must be a local file read plus a cached roster
   lookup — if it needs a network round-trip per edit, someone will turn it off.

---

## 6. Our weakest claim

**That the recording hook fires reliably enough to be trusted.** The design rests on entries
existing. If `PostToolUse` misses edits — a tool we did not wire, a batch write, a script run
through Bash — the index silently under-reports and produces precisely the confident all-clear §3.1
warns about.

**The dirty-state signal is the hedge**, which is the second reason it belongs in the first release.

**Test it by trying to defeat it**: edit a file through Bash rather than the Edit tool, then confirm
the warning still fires for the next session that touches it.

---

## 7. Sequencing — the useful half ships first

| phase | what | why this order |
|---|---|---|
| **1** | **dirty-state warning alone**, PreToolUse | Needs no adoption, no recording, no roster. Works tonight, on today's actual collision. |
| **2** | recording hook + by-file index | Adds *who*, which is what turns a warning into a DM |
| **3** | liveness join | Only worth building once phase 2 produces enough entries for staleness to be the problem |

**Roughly a day for all three.** Each phase is independently useful, and each ships with tests that
must be **proven to go red** — including one per state in §3.1 — per the falsifiability standard
this fleet already holds its guards to.
