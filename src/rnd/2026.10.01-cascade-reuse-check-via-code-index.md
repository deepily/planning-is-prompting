## 1. Summary

1. **The cascade can adopt the check today as a rule about evidence, but the tool cannot answer yet.** The three lookup tools are mounted and the index builds, but the part that asks Jev to compare a need against the index is a stub. Until lupin finishes it, every lookup returns "uncertain, read the source".
2. **The real gap in the cascade is that a "nothing like this exists" ruling carries no evidence at all.** The reviewer is told to grep, and nothing asks what was searched or what came back. The index check fixes that whether or not Jev is live, because every call returns a receipt id.
3. **The tool never decides.** It builds a shortlist. The reviewer rules after reading the source. That is lupin's own design, and this proposal keeps it.

## 3. The proposal

### 3.1 Who and when

| Moment | Who | Tool |
|---|---|---|
| Writing the plan's reuse map | Plan author | `check_exists` per proposed new thing; receipts go in the map |
| Stage 1 of the cascade | Usability/Reuse reviewer | `check_exists` per "new thing" row, then reads source, then rules |
| A `reuse-as-is` or `genuinely-new` ruling is disputed | Counter-reviewer (charter already exists in `workflow/swe-team-roles.md`) | `replay` on the cited receipts, then reads what the reviewer dismissed |
| Reviewing code, not a plan | SWE Reviewer | `fetch_similar` per new definition in the diff. **Not usable in plan review**: it needs a symbol that already exists |

### 3.2 The check, per claimed-new thing

```mermaid
flowchart TD
    A["Section proposes a new thing"] --> B["Reviewer writes the need<br/>in one or two sentences"]
    B --> C["check_exists( need )"]
    C --> D{"Answer"}
    D -->|"REUSE / EXTEND<br/>with a shortlist"| E["Read the source of every<br/>shortlisted and nearest entry"]
    D -->|"NEW"| E
    D -->|"UNCERTAIN, or tool error"| F["Record the cause verbatim"]
    F --> G["Grep, and read what it finds"]
    E --> G
    G --> H["Rule: reuse-as-is /<br/>extend-existing / genuinely-new"]
    H --> I["Row carries receipt id,<br/>what was read, what was searched"]
```

1. **Write the need** from the section's own words: what the new code would do, not what it would be called.
2. **Call `check_exists`** and keep the `receipt_id`, the verdict and, if uncertain, the cause.
3. **Read the source** of every entry on the shortlist and the nearest list. A `NEW` answer does not excuse this: the tool compares one-line descriptions, not behaviour.
4. **Grep anyway.** The index cannot see private helpers, tests, other repositories, another worktree's uncommitted work, or code whose docstring's first line does not describe it. Grep covers what the index is blind to; the index covers same-behaviour-different-name, which grep is blind to.
5. **Rule**, and write the row.

### 3.3 The evidence row

Replaces today's three-column table.

| New thing | Need sent | Receipt | Tool answer | Candidates read (file:line) | Grep: terms, roots, hits | Ruling | Why |
|---|---|---|---|---|---|---|---|

- **A `genuinely-new` ruling with an empty "Candidates read" or an empty "Grep" cell is unsupported**, and the manager classifies it as a finding against the review. This is the cascade's existing rule, *state what you ran, not what you considered*, applied to the one ruling that today needs no evidence.
- **The receipt proves a call happened; the row proves the reviewer used it.** A receipt beside a ruling that ignores the shortlist is a finding.

### 3.4 How the tool's words map to the cascade's

| Tool answer | Cascade ruling | Condition |
|---|---|---|
| `REUSE` | `reuse-as-is` | after reading the candidate |
| `EXTEND` | `extend-existing`, naming the symbol | after reading the candidate |
| `NEW` | `genuinely-new` | only after reading the shortlist and nearest entries, and the grep |
| `UNCERTAIN_READ_SOURCE` | none yet | the reviewer rules from source and grep alone, and says so |

### 3.5 When the tool cannot answer

This is the normal case today, so the rule has to be usable without it.

| Situation | What the reviewer records | What the reviewer does |
|---|---|---|
| `UNCERTAIN_READ_SOURCE` with a cause (`KEY_UNREADABLE`, `CALL_FAILED`, `INDEX_STALE`, …) | the cause, verbatim, and the receipt id | grep plus reading; the row says "index check gave no shortlist: `<cause>`" |
| `NOT_LUPIN_TREE` (any other repository) | that word | grep plus reading; this is every lupin-mobile and planning-is-prompting plan today |
| `REUSE_TOOLS_UNAVAILABLE`, or the tool is not mounted | the error text | grep plus reading |

**Never** write `genuinely-new` on the strength of an answer that was uncertain or absent. **Never** leave the Receipt cell blank without a reason in it: a blank reads as "did not try".

### 3.6 Advisory until a number exists

Lupin's ruling E10 keeps the tools advisory until a recall figure is measured and Rick sets a bar. This proposal follows it: the **receipt and the recorded search are required now**; the **tool's verdict carries no weight in a dispute** until E10 is ruled. When it is, one sentence in the persona file changes.

### 8.3 The plan-time check, per thing a plan step would build

```mermaid
flowchart TD
    A["A plan step would write new code"] --> B["Write the need: what the code does,<br/>in one or two sentences"]
    B --> C["check_exists( need, language )<br/>keep receipt, verdict, cause"]
    C --> D["record_search( receipt_id )<br/>keep search_id"]
    D --> E["Read source: top-rated first, then the<br/>rest of the shortlist, then the five found"]
    E --> F{"Does an existing<br/>definition do the job?"}
    F -->|"yes"| G["REUSED symbol"]
    F -->|"almost"| H["EXTENDED symbol"]
    F -->|"no, after reading all"| I["WROTE_NEW, with the difference"]
    G --> J["Write the outcome line"]
    H --> J
    I --> J
```

1. **Write the need** in the plan's own words: what the code would do, not what it would be called.
2. **Call `check_exists( need, language )`.** Keep the receipt, the verdict and any cause. If the plan changes an existing symbol, also call `fetch_similar` on it; that tool takes only symbols already in the index.
3. **Call `record_search( receipt_id, extra_terms )` every time**, not only before ruling something new. It costs no model call. Pass three to six identifier words you would expect the existing code to use: on the need text alone it found 1 of the 10 answers the index missed (§8.2).
4. **Read source.** The top-rated candidate first, then the rest of the shortlist, then the five `record_search` returns.
5. **Decide**, and write the outcome line (§8.4).

**Reading rules**, written into each workflow that runs the check:

- A shortlisted candidate is a lead, not a match. Expect most of the shortlist to be look-alikes.
- `UNCERTAIN_READ_SOURCE` means "the checker does not know". It never means "nothing exists". Record the cause, read the nearest entries and the `record_search` five, and decide from source.
- No `WROTE_NEW` on a shortlist alone, a score alone, or an uncertain answer alone. It needs the candidates read and the search cited.
- If the tool refuses the repository (`NOT_LUPIN_TREE`) or is not installed, grep, read what grep finds, and write the reason where the receipt would go.

### 8.4 The outcome line

The roadmap's track 3a records what an agent did after each lookup. The plan text can start recording it now, in a shape a script can read later:

```text
REUSE-OUTCOME <receipt id> :: <search id> :: REUSED <symbol> | EXTENDED <symbol> | WROTE_NEW <difference> :: <plan path>#<step>
```

- The plan author writes it in the reuse map when the step is planned.
- The implementer confirms it or writes a second line when the code lands, so a plan that said `REUSED` and shipped new code shows both lines.
- A receipt with no outcome line is a lookup nobody acted on, which is the gap track 3a exists to close.

Whether the server should record the outcome itself (a tool call) is track 3a's design, Sam's. The text line works either way and gives 3a a backlog to ingest.

**Requirement: an outcome checker** (Rick, ruling decision 3, relayed by Cheech 17:31). A checker refuses any line that starts with `REUSE-OUTCOME` and does not match the format above. It also refuses a line whose receipt is not in the lookup log. This is how lupin's `src/lupin_mcp/reuse_exit_gate.py` already treats `RULING` lines. `WROTE_NEW` takes free text: there is no fixed list of reasons.

| Part | Accepted | Taken from the exit gate |
|---|---|---|
| Lead | A line opening with `REUSE-OUTCOME` that the full pattern does not match is refused, and the checker names the line | `RULING_LEAD_RE` with `unparsed_ruling_lines` |
| Receipt | 16 lowercase hex characters, found in `<data>/call-log/*.jsonl` as a `check_exists` or `fetch_similar` call that returned that receipt and logged no error; or the token `excluded` or `unindexed` (see below) | `RECEIPT_ID_RE`, `merge_call_logs`, `receipts_by_symbol` |
| Search id | `rs-` and 10 hex characters, found in the log as a `record_search` call for the same symbol or receipt; or `unindexed` when the receipt slot is `unindexed` | `SEARCH_ID_RE`, `searches_by_symbol` |
| Outcome | `REUSED <symbol>`, `EXTENDED <symbol>`, or `WROTE_NEW <difference>` (any text that does not contain ` :: `) | The `DISTINCT <why>` free-text clause |
| Location | `<plan path>#<step>`, no spaces | none |

A sketch of the pattern, for the author:

```text
^\s*REUSE-OUTCOME\s+(?P<rid>[0-9a-f]{16}|excluded|unindexed)\s+::\s+(?P<sid>rs-[0-9a-f]{10}|unindexed)\s+::\s+(?P<outcome>REUSED\s+\S+|EXTENDED\s+\S+|WROTE_NEW\s+\S.*?)\s+::\s+(?P<where>\S+#\S+)\s*$
```

**Settled by Cheech for the plan, 17:34 and 17:35.** These were outside Rick's ruling, and they are Cheech's rules, not Rick's; the plan says so.

1. **Lines that cannot have a receipt** use one fixed token in the receipt position, as the exit gate does. `excluded` is for an `EXCLUDED_*` refusal, and the checker accepts it only when the log holds that refused call. `unindexed` is for a file outside the index or outside the tree, `NOT_LUPIN_TREE` included. The log holds nothing to check `unindexed` against, so as with the gate, the reader challenges it.
2. **The search id is checked against the log too**, as the gate's `searches_by_symbol` does.
3. **The checker lives in lupin** beside `src/lupin_mcp/reuse_exit_gate.py`, ideally sharing its log reader (`merge_call_logs`).
4. **An `unindexed` line carries `unindexed` in both id slots**, and its reviewer challenges it, as the gate's reader does today (Cheech, 17:35). The token rule is Cheech's, not Rick's.
