## Symptom

Since the tmux-server-death debugging (2026-07-13/14), **no freshly spun Claude Code instance appears on the notifications-app focus bar** — name, color, and icon render only after the operator manually asks the session to set its session topic. Reproduced on every spawn since, including all of today's cascade reviewer spawns (3-4 recurrences in 10 minutes during cascade staffing).

## Root cause — the five-link chain (each link receipt-verified)

1. **The focus-bar roster is notification-derived.** `get_visible_senders` (lupin `src/cosa/rest/routers/notifications.py:2508`) lists senders that have **at least one visible notification row**. A session that has pushed nothing is invisible, no matter how alive it is.
2. **The intended "birth certificate" is the SessionStart hello-world.** The registration hook (`src/lupin_cli/claude_code/hooks/register_session.py`, Phase 5 ~line 1164) fires a TTS notification with the session's `sender_id` on every fresh start — that notification is what used to paint new sessions onto the bar.
3. **`send_tts()` fails silently without `LUPIN_DEV_EMAIL`.** `hook_common.py:221` (`get_target_email`) reads the env var only — no file fallback — and `send_tts` **returns silently** when it's absent. (`HOOK_TTS_ENABLED` defaults to enabled, so the email is the single gate.)
4. **The tmux-server restart lost the variable.** The fleet-killer fix restarted the tmux server; a tmux server freezes its global environment from whatever context creates it (`tmux start-server` does not seed it; the first `new-session` freezes it — Krishna's same-family finding, store `6144b864`). The new server's context was non-login → no `~/.bashrc` exports. **Verified live: `tmux show-environment -g` contains no `LUPIN_DEV_EMAIL`** (checked 2026-07-15 ~14:15 EDT). The pre-wipe long-lived server had inherited it from Rick's login shell.
5. **Therefore**: every hello-world since the restart no-ops **silently** → no notification row → no focus-bar entry → the session appears only after its first MCP-side push (e.g. `set_session_topic`), because the MCP server uses **server-side credentials** and never depends on pane env.

This explains both observed facts exactly: *all* instances are affected, and a manual topic-set cures each one.

## Why fix 4 matters even after 1–3 land

The hello-world path depends on pane environment, which this incident proved can vanish silently and stay broken for days. The MCP topic-push path is env-independent. Making the topic push a boot obligation means operator visibility survives the next environment accident — a mechanism at the session's own layer, not a hope about the substrate.

## Live addendum (updated ~14:55 EDT) — a SECOND bug is now CONFIRMED for spawned seats

Escalation of the earlier wrinkle: the cascade seats fired **4/4 `notify()` (server-accepted, "sent (queued)") and 4/4 `set_session_topic` (`ui_push: ok`) — and Rick remained blind to all of them**. So for manager-spawned sessions, the drop is **downstream of server accept**: the env-var chain above explains the dead hello-world (hook path), but it is NOT the whole story — the MCP path is also failing to *deliver/render* for these seats, while succeeding for interactively-launched sessions (this author's own notifications reached Rick all afternoon).

- Sharpest discriminator (now with the fix team): does a **notification DB row** exist for the spawned sender? Row-present → client/roster rendering; row-absent → drop between accept and persist.
- Candidate mechanism worth checking first: **recipient resolution** — spawned sessions authenticate under per-project machine accounts; if their notifications persist targeted at a different `user_id` than Rick's, `get_visible_senders` (which is per-recipient) never lists them, no matter how many pushes succeed.
- "Queued ≠ delivered" is now a proven law of this incident: a worker's "my notify fired" self-report is not a delivery receipt. The fix's acceptance test asserts **actual render**, not queued-status (Mr Radio's author seat, lupin bug `ef10c5b6` + `179fe3ab`).
