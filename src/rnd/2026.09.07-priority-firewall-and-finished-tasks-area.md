## 1. The declarations of fact

Operator rulings. Not open for redesign; the implementer does not get a vote on their consequences.

| # | Declaration |
|---|---|
| **D1** | **Default priority on every creation path is `P5`.** Every UI form, every endpoint, every creation helper. No path may default higher. |
| **D2** | **The priority range is `P0`–`P5`**, inclusive, everywhere a priority is edited — task, holding, and epic accordions alike. |
| **D3** | **P5 → P4/P3/P2/P1 requires the operator OR a manager.** A worker cannot raise its own row. |
| **D4** | **P0 is the operator alone.** No manager, no worker, no automation, no emergency exception. *"I don't give a fuck if the server is on fire."* |
| **D5** | **Workers may file `P5` and only `P5`.** Anything higher is a manager petition to the operator. |
| **D6** | **Only the operator or a manager may PULL from holding and ASSIGN.** Worker self-pull and self-assign are ended. |
| **D7** | **Every pull from holding takes the highest-priority available row.** Cherry-picking is over. |

### D4 is a firewall, not a permission check

A permission check asks *"is this caller allowed?"* and is satisfied by a caller who **claims** to be a manager. A firewall means the write is refused for every principal except the operator — managers, the system, and migration scripts included.

⚠️ **This is already broken today.** Mr. Radio reports `payload.actor` is **caller-declared** (his firewall row `b8205986`). A self-asserted actor field cannot carry D3 and must never carry D4. See §5 R2 for Rick's ruling.

### A3 — The authorization ladder

| Transition | Who may |
|---|---|

### A5 — Highest-priority-first on pull

Order candidates by priority ascending-by-number; taking a lower row than the highest available is refused. Per the 09.06 doc's R2 a legitimate skip is a **written reason stamped on the skipped row** — under D7 that reason is now the *manager's*, not the worker's.
