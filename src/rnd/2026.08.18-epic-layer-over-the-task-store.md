> 🔴 **THE BOARD IS 37 ROWS, NOT 28 — AND THE AUDIT IS WHAT FOUND THAT.**
> My first pass grouped 28 rows and reported that number to Rick. It was wrong, and the mechanism is worth more than the correction: `task_query` **hides park-active rows by default**. Nine rows — including a **P1** (`60f04102`, "any authenticated user can run arbitrary pytest args as a subprocess") — were invisible to my own audit. They are not lost work; each has a chase and will rejoin the owed count on its own. But an audit that certifies the board clean while nine rows sit outside its frame is the exact defect this fleet keeps filing: **a green report from an instrument that cannot see.**
> ⇒ Every epic query and every audit run below carries `include_parked=True`.

## 1. The short answer

He was right, and the field already existed.

Every row in the store carries a **`correlation_key`**. It is indexed, it is an exact-match filter on `task_query`, and it was **null on all 37 open rows**. Nobody had ever written one. The epic layer was unbuilt, not absent.

It is now stamped. One filter returns one epic:

```
task_query( correlation_key="epic:cj-flow-v2-ship", terse=True )   →  9 rows
```

**Why a periodic summary would have been the weaker choice.** A summary is re-derived each time from rows that do not carry the story, by whoever reads all 37 and reconstructs the intent. It is right the day it is written and drifting by the end of the week, and the store gets no better. Putting the answer in a field makes the summary a *render* instead of an *act of memory*.

## 4. Keeping it true — the proposed rules

Grouping today's board is one pass. Keeping it honest needs a rule, or we are back here in a week with a page that lies.

### 4.1 The rule

**Every row names its epic at creation.** `task_create` already accepts `correlation_key`; this costs one argument.

```python
task_create( item_class="bug", project="lupin", title="…",
             correlation_key="epic:seal-the-test-tier" )
```

### 4.2 Naming

`epic:<short-kebab-slug>`. The **`epic:` prefix is load-bearing** — it is what makes a non-epic value visible at a glance, and it is the whole reason drift is detectable (see 4.5).

### 4.3 No blanks — `epic:unassigned` is explicit

Work that genuinely belongs to no epic gets `epic:unassigned`, never a blank. **A blank is indistinguishable from forgetting**, and a rule you cannot audit is a preference.

### 4.4 Who mints a new epic

A **manager**. A worker picks from the existing set or uses `epic:unassigned` and says so in the body. This keeps the epic list short enough to read, which is the entire point — an epic layer with forty epics is the flat list again.

### 4.5 The audit — ✅ BUILT AND PROVEN

**The obvious version does not work.** `terse=True` does not return `correlation_key` at all, and `task_query(correlation_key=…)` is exact-match with no `NOT LIKE`. Reading non-terse to see the field returns every row's full body — tens of thousands of tokens, impractical as a routine check.

**So invert it — a set difference over cheap terse reads:**

```python
all_rows = task_query( unscoped_audit=True, terse=True, include_parked=True, limit=300 )
grouped  = set()
for key in KNOWN_EPIC_KEYS:
    grouped |= { t["id"] for t in task_query( correlation_key=key, terse=True,
                                              include_parked=True )["tasks"] }
drift = { t["id"] for t in all_rows["tasks"] } - grouped
```

**Both controls were run on the live store, not asserted:**

| # | Control | Result |
|---|---|---|
| 1 | Mint a row with **no** key (`8b6b05be`) | ✅ named in `drift` |
| 2 | Stamp a `cc-task:…` key over a live epic key (`697a85fe`) — a simulated §7 adoption | ✅ named in `drift`; its epic went 3 → 2 |

Arithmetic: full list **38**, twelve epic queries summed to **36**, `drift` = exactly those two ids, no false positives. Both restored in the same turn — `697a85fe` re-stamped (event 7940), the probe dropped with its reason (event 7941).

**Control 2 is the one that matters.** It is the only proof that an adoption eating an epic key is *detectable* rather than invisible — and adoption is existing, correct practice under §7, not a hypothetical.

Full procedure, and the rule it enforces: `workflow/task-store-discipline.md` §7.1.

This document is a snapshot. The durable artifact is the field. Regenerate rather than edit — a hand-edited page drifts from the store and then there are two answers.

## 5. Honest limits of what was done tonight

**We are `correlation_key`'s third user, and its declared purpose is something else.** `postgres_models.py:1436` documents it as *"harness TodoWrite/TaskList ↔ store uuid correlation (C1 upsert key)"*. That use is dead — the harness→store mirror was retired at the 2026-06-17 cutover. But `task_correlate` is live and writes per-row-unique adoption keys into the same field.

**Why it still works today**, checked rather than assumed:
- the index (`idx_task_items_correlation_key`) is **non-unique**, so many rows may share a key;
- `task_query(correlation_key=…)` is an exact-match filter that returns a **list** — a shape that only makes sense if grouping was anticipated;
- it was null on all 37 rows, so nothing was displaced.

**A third informal convention was already in play.** Two rows carried a key before tonight, and both held a *parent row id* rather than an adoption key — `d212f54b` held `92062fe2-…`, `89b27996` held `f924ca02`. Both are preserved in the event log (`re-correlated` events 7904 and 7909) and both parents sit in the same epic, so nothing was lost. But it means three different meanings had been reached for in one field.

**The proper home is a dedicated field.** Two changes, both in lupin:
1. an `epic` column, so the grouping cannot be clobbered by an adoption;
2. `epic` added to `VALID_ITEM_CLASSES` (currently `task · decision · review_request · bug · gate`), so an epic can be a **row that carries its own story** — which is what Rick actually described, and what this document is standing in for.

**No epic rows were minted tonight**, deliberately. Forcing them in as `task` rows would put six non-work items on the owed-work board and make the burn-down number fiction — which is the same class of defect as the parked-row problem the store already solved.
