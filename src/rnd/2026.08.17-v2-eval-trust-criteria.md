## 1. The sample signature — what a result must carry to be a result at all

A number missing any of these is **not a weak result; it is not a result.** Do not interpret it, do
not put it in a table, do not average it with anything.

**Already bound by the harness** — `PROVENANCE_FIELDS` (`paired_eval.py:76`), compared field-by-field
by `paired_provenance_check` (`:154`), which `build_paired_verdict` runs **first** and refuses on:

| field | what it pins |
|---|---|
| `arm` | which arm this stamp describes |
| `corpus` | the utterance source both arms drew from |
| `seed` | so a re-run is the same sample (plan §1.4a) |
| `n_per_command` | the stratification width |
| `sample_signature` | the authoritative binding — computed from the sampled pairs themselves |
| `sampled_n` | how many utterances were actually measured; `0` on either arm is refused outright |

**🔴 Two things the signature does NOT currently carry, and both belong in it:**

1. **The sha read back from the RUNNING server.** `assert_measured_sha` exists and does exactly the
   right thing — it reads `/api/code-identity` from the live process and **raises**
   `EvalIntegrityError` rather than stamping a baseline measured against the wrong tree. Sam built it
   for precisely this failure and its docstring names the root cause: *"every wrong answer arrives as
   a plausible number rather than an error."* But it is called at `v1_eval_arm.py:680` — **the v1 arm
   only** — and the observed sha does **not** travel into `PROVENANCE_FIELDS`. So the v1 arm fails
   loud on a wrong tree while the v2 arm has no equivalent check, and neither sha appears in the
   artifact a reader later audits. **Do not reinvent it — call it on both arms and put both observed
   shas in the stamp.**
2. **The venue.** Nothing in the stamp records that the run happened on `:8000` under monopolize
   rather than side-doored against a dev server. Two arms measured in different venues would pass
   every existing provenance check.

**Rule**: a result is trustworthy only if its stamp carries all six existing fields **plus** both
observed shas **plus** the venue, and the two arms agree on every one of them.

## 2. The numbers the plan actually needs

Named precisely, with their source. **`PASS_FRACTION = 0.20` is the only threshold in code**
(`paired_eval.py:80`); everything else below is a comparison, not a margin — which is itself a finding
(see §5).

### 2a. The two headline metrics (plan §1.1)

| metric | the number | bar |
|---|---|---|
| **Latency** | paired median Δ (v1 − v2), positive ⇒ v2 faster, over the shared utterances | Δ ≥ **20%** of the v1 median. This is the gate that fires or declines |
| **Cache-hit rate** | warm-pass hit rate, **absolute number for each arm**, not just the delta | v2 ≥ v1 on the same corpus |

Two qualifiers that must travel with those numbers:

- **The instrument string prints in the verdict table, not in prose** (Cheech's ruling, carried into
  `INSTRUMENT` at `paired_eval.py:85`). v1's span **includes its full FIFO queue-dwell**; v2 is one
  synchronous round-trip with no queue. A reader who takes `delta_ms` for a compute-only difference
  has been misled, and the caveat has to sit next to the number to prevent it.
- **A hit is a tier-1 exact match** via `question_normalized` string equality (`find_exact_normalized`,
  handoff R-C1) — **not** a float comparison against `100.0`. The float path understates the very
  number the experiment exists to measure.

### 2b. The floors — vetoes, not scores (plan §1.2, §1.4b(2))

Any one at FAIL forces **STOP** regardless of how good the headline numbers look, and the report must
print an `OVERALL` line stating `INVEST` / `STOP` / `SPLIT — port the shape` **computed**, so the
decision is printed rather than inferred.

| floor | bar |
|---|---|
| Routing accuracy | v2 ≥ v1 on the shared corpus |
| Replay correctness | hand-checked sample of cache hits, **≥ 30 utterances**, **zero** answers to a materially different question |
| No new silent failures | `router_error`, `extract_error`, `replay_failed`, `agent_error` each appear in the trace with a **distinct** value |
| v1 untouched | v1's existing suites green, `expedite()` output unchanged |

**The replay-correctness floor is human-executed and the harness must not pretend otherwise.** Every
row carries an `EXECUTOR`. R-C2 (matched snapshot's `routing_command` ≠ the utterance's expected
command) is a **one-way pre-filter that can only ever FAIL a row** — agreement does not pass it,
because the same command with a different city is still the wrong answer. The floor stays
`EXECUTOR: HUMAN` and unchecked rows print `PENDING HUMAN`, never a checkmark. R-C2 is a **lower
bound** and under-counts; keep that caveat verbatim.

### 2c. Control-logic size (plan §1.3)

`ast` walks both request paths and counts — a real number, not a vibe, and falsifiable in the
direction that matters:

| quantity | v2 target |
|---|---|
| statements on the request path | ≤ **200** |
| distinct command→agent mechanisms | **1** |
| cache lookups per request | **1** |
| places a request can block on a human | **0** |

If v2's flow lands over 200, **the "minimal control logic" claim failed**, whatever the latency did —
say so in the report rather than quietly widening the target.

### 2d. The decision rule (plan §1.4)

STOP requires **both**: not meaningfully faster (§1.1 margins unmet) **and** not meaningfully smaller
(§1.3 unmet). Either alone earns a conversation. And the pre-registered better-than-a-win case:
**not faster but much simpler ⇒ port v2's structure onto v1** rather than keeping two flows.

## 4. What should RAISE, not report

**A note telling readers not to trust a file is not a guard.** John's warning about `paired-run-latest`
is correct and will be forgotten by the third reader. These are the criteria that should fail the run
rather than appear in its output:

| criterion | today | should be |
|---|---|---|
| Observed sha on **v1** | ✅ **raises** (`assert_measured_sha`) | keep |
| Observed sha on **v2** | ❌ nothing | **raise** — same function, second call site |
| Both shas in the provenance stamp | ❌ not in `PROVENANCE_FIELDS` | **add**, so the audit is possible after the fact |
| Venue recorded and matched across arms | ❌ nothing | **add to the stamp; refuse on mismatch** |
| Provenance binding (corpus/seed/n/signature) | ⚠️ refuses with a reason, **never raises** | correct at the library seam. **The run's entry point should exit non-zero** on `provenance_ok: False` — a DECLINE that leaves a green exit code reads as a pass to anything automated |
| Reading `paired-run-latest` | ⚠️ a note in a doc | **assert** the file's `sample_signature` equals this run's before reading a single number out of it. This is D1/D7 and it is the one that has already bitten |
| `sampled_n` plausibility | ❌ nothing | **raise** when `sampled_n` is not what the declared sampling rule implies — D1 in one assertion |
| Floors → OVERALL | ⚠️ §1.4b(2) requires a computed `OVERALL` line | **compute and print it.** A report where floors fail while the headline rows pass, and nothing says STOP, shows the reader green |

**The library keeps returning refusal dicts — that is right.** `build_paired_verdict` should not raise;
it is a pure function over two artifacts. The change is at the **caller**: the run must treat every
refusal as a failed run, not as a result with a caveat.

## 5. Open questions — where the plan does not define a number it needs

Standing rule: **no guessed numbers sitting among measured ones.** These are for María to rule on
**before** the re-run lands, not for me to fill in.

**Q1 · Does the p95 bar still exist?** §1.1 states *"v2 p95 must not be worse than v1 p95"* as part of
the latency bar. §1.4b(3) then establishes that at n=60 the p95 is about the third-largest value and a
single slow LLM call moves it — and the harness accordingly renders p95 **labelled INFORMATIONAL, n
too small to gate** (`paired_eval.py:358`). **Those two cannot both govern.** Either the p95 bar is
retired in favour of the paired median Δ (which I read as the intent of the correction), or it needs a
tolerance — and **the plan states no tolerance**, so I am not inventing one.

**Q2 · Do the `v2 ≥ v1` floors mean literally ≥, at n=60?** Routing accuracy and cache-hit rate are
both written as bare comparisons while latency got a pre-registered 20% margin. At 60 utterances per
command a **single** utterance flips a bare ≥. The plan itself argues the case against direction-
without-margin: *"'Faster' is not a result… noise wearing a number's clothes."* The same objection
applies to `≥` here. Either the ≥ is deliberate (a floor is meant to be strict) or these need margins.
**A margin invented now, after the design is built, is exactly what this document exists to prevent.**

**Q3 · How is the ≥30-utterance replay-correctness sample drawn?** The floor names a size but not the
draw. If it is not seeded from the same sample the arms measured, the hand-check is auditing a
different population than the hit-rate number it is supposed to qualify.

**Q4 · What is the `n_shared` floor for D6?** The gate declines only at *zero* shared pairs. A run that
pairs 12 of 480 fires and produces a real-looking number. **The plan does not say how thin is too
thin**, and I will not pick a fraction.

## 6. The one-line version

**A v2 eval number is trustworthy only if it carries a full sample signature — including a sha read
back from the running server on BOTH arms and the venue — was produced by a run that dumped its
artifacts, and is read out of a file whose signature matches this run. Everything else on this page is
that sentence with its receipts.**
