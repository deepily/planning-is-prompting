## 1. The sample signature — what a result must carry to be a result at all

A number missing any of these is **not a weak result; it is not a result.** Do not interpret it, do
not put it in a table, do not average it with anything.

**Already bound by the harness** — `PROVENANCE_FIELDS` (`paired_eval.py:76`), compared field-by-field
by `paired_provenance_check` (`:154`), which `build_paired_verdict` runs **first** and refuses on:

| field | what it pins |
|---|---|
| `arm` | which arm this stamp describes |
| `corpus` | the utterance source both arms drew from |
| `seed` | so a re-run is the same sample (plan §1.4a) |
| `n_per_command` | the stratification width |
| `sample_signature` | the authoritative binding — computed from the sampled pairs themselves |
| `sampled_n` | how many utterances the arm **intended** to measure (`len( sampled_pairs )`) — ⚠️ **not** how many it actually measured; `0` on either arm is refused, but that guard is measuring the wrong subject — see §7b |

### 1a. 🔴 The auditability gap, stated precisely

> **Correction to my own first draft.** I wrote that the observed sha "never reaches the stamp." That
> is wrong, and the truth is more interesting: **it reaches the stamp but not the contract.**

**What is actually true, verified line by line:**

| # | fact | evidence |
|---|---|---|
| 1 | The v1 arm **does** read the sha back from the running server and **raises** on a wrong tree | `assert_measured_sha( read_sha_fn( base_url ) )`, `v1_eval_arm.py:680` |
| 2 | That observed sha **is** carried into the v1 provenance dict, deliberately — the code comment insists it is the OBSERVED value, "never `V1_PIN_SHA`," because stamping the constant would read `b0735467` no matter what actually ran | `provenance[ "v1_arm_git_sha" ] = observed_sha` |
| 3 | It **is** rendered in the report, as a `v1 arm sha` row | `render_provenance_block`, `paired_eval.py` |
| 4 | **But `v1_arm_git_sha` is not in `PROVENANCE_FIELDS`** — that tuple is `arm, corpus, seed, n_per_command, sample_signature, sampled_n` | `paired_eval.py:76` |
| 5 | So `_missing_provenance_fields` **cannot report it absent** (it iterates `PROVENANCE_FIELDS`) and `paired_provenance_check` **never compares it** (it loops four binding fields only) | `paired_eval.py:154` |
| 6 | The v2 arm reads **no sha at all** — `grep` for `code-identity`, `git_sha`, `measured_sha` across `v2_eval.py` returns **nothing**. It stamps `make_provenance( "v2", … )` and writes `{metrics, provenance}`: six fields, no tree identity | `v2_eval.py:1021, 1048` |
| 7 | **There is no v2 pin to check against even if someone wired the read.** `V1_PIN_SHA` (`v1_eval_arm.py:105`) is the only pin in `src/scripts` | `grep '_PIN_SHA ='` |
| 8 | The asymmetry is **deliberate, not an oversight** — the render's own comment reads "v1-only (the v2 arm has no pinned-tree constraint), so v2 renders `—`" | `render_provenance_block` |

**Why the combination is worse than either half.** The sha is **rendered but not required.** A run that
never called `assert_measured_sha` produces a stamp with no `v1_arm_git_sha`, passes
`paired_provenance_check` intact, and renders `—` in the sha row. **A missing sha and a legitimately
absent one are the same character on the page.** Nothing downstream can tell a reader which one they
are looking at — and answering "which tree produced this number" is the entire reason that column
exists.

**The deliberate choice has also expired.** Pinning v1 alone was right when v1 was the **baseline being
protected** — you pin what you measure *against*. **v2 is now the thing under evaluation**, and it is
the arm whose code changed five times today (John's five fixes, each on a wip branch). The arm most
likely to be running a different tree than anyone believes is the one with no check at all.

⚠️ **One thing I checked and did NOT find**, so it does not become a rumour: v2's `make_provenance` call
passes a local named `corpus`, which reads like the full corpus — but it is the output of
`stratified_sample` two lines above (`v2_eval.py:1019-1021`), the same sampler v1 uses. **Both
signatures are computed over the same population. There is no signature bug here.**

### 1a′. Would a missing sha be CAUGHT? Walk it through — the answer is no, at every seam

The gap above is easy to read as *"the sha is weakly covered."* It is not weakly covered. **Nothing
catches it.** Below is the actual case — a run whose sha read never happened — traced against every
check the pipeline has, today.

| # | check | does it catch a missing sha? | why |
|---|---|---|---|
| 1 | `assert_measured_sha` | **only if it is CALLED.** The failure mode *is* that it was not | It raises on a wrong or empty sha — but a call that never happens cannot raise. This is a guard on the value, not on its own invocation |
| 2 | `_missing_provenance_fields` | ❌ **NO** | It iterates `PROVENANCE_FIELDS`, and `v1_arm_git_sha` is not in that tuple |
| 3 | `paired_provenance_check` | ❌ **NO** | It compares four binding fields — `corpus`, `seed`, `n_per_command`, `sample_signature`. The sha is not among them |
| 4 | `build_paired_verdict` | ❌ **NO** | It refuses only when check 3 returns a reason; check 3 returned `None` |
| 5 | The gate itself | ❌ **NO** | It computes a median over spans. A number's arithmetic is unaffected by which tree produced it |
| 6 | `render_provenance_block` | ❌ **NO — this is where it becomes invisible** | `v1_provenance.get( 'v1_arm_git_sha', '—' )`. **The `—` default is the fallback for a legitimately-unpinned arm, and it renders identically for an arm whose check never ran** |
| 7 | The v2 arm, any check at all | ❌ **NO** | v2 reads no sha, so there is nothing to be missing — the column is blank by design and blank by failure at the same time |
| 8 | A human reading the report | ❌ **NO, and this is the point** | The row is present, the table is complete, the provenance line says **MATCH**. Nothing on the page distinguishes *"we checked, this arm has no pin"* from *"we never looked"* |

**Verdict: a run with no sha read produces a report that is indistinguishable from a correct one.**
Not a weaker report, not a caveated report — **identical output.** It renders a dash, passes the
provenance check, prints **MATCH**, and emits a median-Δ verdict. There is no seam at which the
absence surfaces.

**After the fixes in §1b, check 2 catches it** — `v1_arm_git_sha` and `v2_arm_git_sha` inside
`PROVENANCE_FIELDS` means a stamp without them is a **missing field**, which `_missing_provenance_fields`
names and `build_paired_verdict` refuses on, **before any latency number is emitted.** That is the
whole value of moving one string into one tuple: it converts an invisible absence into a refusal that
names itself.

⚠️ **And the dash must not survive the fix.** If the shas become required and the renderer still prints
`—` on absence, the report will show a blank next to a run that was refused — the same ambiguity one
layer down. **Render the refusal, not a placeholder.**

#### The family this belongs to

This is not a novel failure. It is the fourth instance this project has recorded of **incomplete
presented as complete**, and the three siblings are all in the store:

| receipt | the shape |
|---|---|
| `f3beb6d5` — *"Test-suite report says ALL PASSED — e2e for a 5-of-N run"* | a partial run rendered as a full green |
| Mr Radio's retraction on `92062fe2` — wrote **"scheduled"** as though it meant **"ran"** | an intention rendered as an outcome |
| `paired-run-latest` holding **v1=3 / v2=2** on a live-sized run | stale unit data rendered as this run's result |
| **this one** — a `—` in the sha column | an unperformed check rendered as a checked-and-empty one |

**The common mechanism, worth naming once**: in every case the *absence of evidence* was rendered in
the same visual slot as *evidence of absence*, and the reader had no way to tell them apart. A blank
that means "not applicable" and a blank that means "never ran" must not be the same character.

### 1b. What the stamp must carry to be auditable

The test is not *"did the run check itself."* It is **"can someone six weeks from now, holding only the
artifact, say which trees produced this number and where it ran."** Today that answer is no for both
arms: v1's sha is present but unenforced, v2's was never read.

| field | today | required |
|---|---|---|
| `arm`, `corpus`, `seed`, `n_per_command`, `sample_signature` | ✅ in the contract, compared, refused on mismatch | keep |
| `sampled_n` | ⚠️ in the contract, but it counts **intent** — its `== 0` emptiness guard cannot detect an arm that measured nothing (§7b) | keep it as the denominator, and add the outcome count beside it |
| `ok_n` / `n_ok` (the outcome count) | ❌ lives in `metrics`, not in the stamp — so the pairing check never sees how much either arm actually measured | **add to the stamp**, and make the emptiness guard read it |
| `v1_arm_git_sha` | ⚠️ stamped and rendered, **not** in the contract | **move into `PROVENANCE_FIELDS`**, so absence is a refusal rather than a dash |
| `v2_arm_git_sha` | ❌ does not exist | **add** — same `assert_measured_sha`, second call site, against a v2 pin that must also be created |
| `venue` | ❌ does not exist | **add** the `base_url` each arm actually talked to, so a side-doored arm cannot pass as a monopolize run |
| `run_id` | ❌ not stamped | **add** the submitting job id, so an artifact can be tied to the run that claims it — this is what makes D8 detectable |
| `completed` | ❌ not stamped | **add**, written at dump time. An artifact with no completion marker is a partial run, which is D2 |

**Rule**: a result is auditable only if its stamp carries all six existing fields **plus both arms'
observed shas, the venue, the run id, and a completion marker** — and the arms agree on every field
that must match. **A field that is rendered but not required is decoration.**

## 2. The numbers the plan actually needs

Named precisely, with their source. **`PASS_FRACTION = 0.20` is the only threshold in code**
(`paired_eval.py:80`); everything else below is a comparison, not a margin — which is itself a finding

### 2a. The two headline metrics (plan §1.1)

| metric | the number | bar |
|---|---|---|
| **Latency** | paired median Δ (v1 − v2), positive ⇒ v2 faster, over the shared utterances | Δ ≥ **20%** of the v1 median. This is the gate that fires or declines |
| **Cache-hit rate** | warm-pass hit rate, **absolute number for each arm**, not just the delta | v2 ≥ v1 on the same corpus |

Two qualifiers that must travel with those numbers:

- **The instrument string prints in the verdict table, not in prose** (Cheech's ruling, carried into
  `INSTRUMENT` at `paired_eval.py:85`). v1's span **includes its full FIFO queue-dwell**; v2 is one
  synchronous round-trip with no queue. A reader who takes `delta_ms` for a compute-only difference
  has been misled, and the caveat has to sit next to the number to prevent it.
- **A hit is a tier-1 exact match** via `question_normalized` string equality (`find_exact_normalized`,
  handoff R-C1) — **not** a float comparison against `100.0`. The float path understates the very
  number the experiment exists to measure.

> 🔴 **Before computing ANY rate on this page, read §10 — the denominators are pinned there.**
> Eight of the ten places two readers would diverge are settled (cache-hit, routing accuracy,
> degradation-path names, failure rate, latency instrument, declared `n`, `n_shared`, clustering);
> two are escalated as labelling rulings. A rate computed without its pinned denominator is not a
> disagreement waiting to happen — it is one that has already happened and nobody has noticed yet.

### 2b. The floors — vetoes, not scores (plan §1.2, §1.4b(2))

Any one at FAIL forces **STOP** regardless of how good the headline numbers look, and the report must
print an `OVERALL` line stating `INVEST` / `STOP` / `SPLIT — port the shape` **computed**, so the
decision is printed rather than inferred.

| floor | bar |
|---|---|
| Routing accuracy | v2 ≥ v1 on the shared corpus |
| Replay correctness | hand-checked sample of cache hits, **≥ 30 utterances**, **zero** answers to a materially different question |
| No new silent failures | `router_error`, `extract_error`, `replay_failed`, `agent_error` each appear in the trace with a **distinct** value |
| v1 untouched | v1's existing suites green, `expedite()` output unchanged |

> ⚠️ **`agent_error` on the V1 ARM HAS NO LIVE PRODUCER — added 2026-08-17 ~17:30 EDT, verified in
> lupin, refutable by one call site.** The v1 arm tags `agent_error` when completion metadata carries a
> non-empty `error` (`v1_eval_arm.py:330`), but nothing real ever hands it that: the arm captures
> metadata **only** on a `"completed"` transition (`:486`), while the one emitter carrying a real error
> message rides `FAILED` (`running_fifo_queue.py:867`, emitted at `:880`). All five COMPLETED emitters
> — plus the STALLED one — hardcode `error = None` (dicts at 599, 713, 1416, 1622, 1698, 1906). A v1
> failure therefore lands `ok=False, failure="no_completion"`, never a tagged success.
>
> **Two consequences when reading a v1 report.** (1) The floor above gates **v2's redesign**, not v1's
> baseline — v1's degradation column is informational, and an empty `agent_error` there is expected,
> not a defect. (2) If a v1 artifact **does** show `agent_error`, either its input was synthetic or a
> producer exists that this sweep missed — **find the call site before believing the number**. Refute
> this note with a COMPLETED emitter carrying a non-empty `error`; a fixture does not refute it. Both
> Krishna and Tiberius advanced the opposite claim from hand-built input and withdrew it independently
> once the emitters were read.

**The replay-correctness floor is human-executed and the harness must not pretend otherwise.** Every
row carries an `EXECUTOR`. R-C2 (matched snapshot's `routing_command` ≠ the utterance's expected
command) is a **one-way pre-filter that can only ever FAIL a row** — agreement does not pass it,
because the same command with a different city is still the wrong answer. The floor stays
`EXECUTOR: HUMAN` and unchecked rows print `PENDING HUMAN`, never a checkmark. R-C2 is a **lower
bound** and under-counts; keep that caveat verbatim.

### 2c. Control-logic size (plan §1.3)

`ast` walks both request paths and counts — a real number, not a vibe, and falsifiable in the
direction that matters:

| quantity | v2 target |
|---|---|
| statements on the request path | ≤ **200** |
| distinct command→agent mechanisms | **1** |
| cache lookups per request | **1** |
| places a request can block on a human | **0** |

If v2's flow lands over 200, **the "minimal control logic" claim failed**, whatever the latency did —
say so in the report rather than quietly widening the target.

### 2d. The decision rule (plan §1.4)

STOP requires **both**: not meaningfully faster (§1.1 margins unmet) **and** not meaningfully smaller
(§1.3 unmet). Either alone earns a conversation. And the pre-registered better-than-a-win case:
**not faster but much simpler ⇒ port v2's structure onto v1** rather than keeping two flows.

## 4. What should RAISE, not report

**A note telling readers not to trust a file is not a guard.** John's warning about `paired-run-latest`

### 4a. The three seams, and which behaviour belongs at each

A criterion is not simply "an assertion" or "a report" — **where it fires decides whether it can be
ignored.** Three seams, three different correct behaviours:

| seam | what it is | correct behaviour | why |
|---|---|---|---|
| **Measurement boundary** — inside an arm, at the moment it touches the live server | `assert_measured_sha` sits here | **RAISE, before spending.** | The v1 arm proves the tree *before* running two passes. An integrity failure caught after three hours of measurement has already cost the run |
