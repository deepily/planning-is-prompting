## 11. Part B: the pruning pass over `workflow/`

This is the work you described: finding rules we wrote over fifteen months that Claude Code now does on its own.

**The ruling I need first**: what counts as "Claude Code does this already". My proposed test, per rule: *a current Claude Code feature covers it, and I can name the feature and show it working in this fleet.* A rule that only resembles a feature stays.

**Method, per workflow doc**

1. Split the doc into its separate rules.
2. Sort each rule into one of four bins:

| Bin | Meaning | Action |
|---|---|---|
| **Native** | Claude Code now does this without being told (for example: tracking a task list, worktree isolation, memory files, skills loading on demand, scheduled wake-ups) | Candidate to delete, with the feature named |
| **Mechanized** | One of our own scripts or hooks now enforces it | Shrink the prose to one line pointing at the script |
| **Ours** | Fleet-specific: personas, the task store, mementos, the voice server, your rulings | Keep |
| **Unknown** | Cannot tell without a trial | Keep, and list for a trial |

3. For every Native candidate, run the behavior once **without** the rule in a scratch session and record what happened. No trial, no cut.
4. Report per doc: rules counted, bin totals, proposed cuts with their evidence.

**Pilot**: five docs chosen to span the range, for example `session-start.md`, `session-end.md`, `testing-baseline.md`, `history-management.md`, `plan-serialization.md`. The pilot tells us how much is really Native before we spend on all 65. I have not read these for this purpose, so I am not predicting the result.

**Crew for the full pass, if the pilot justifies it**: one seat sorting, one seat running the no-rule trials, one reviewer. Cuts land as one commit per doc so any one can be reverted alone.

**What Part B will not do**: touch your rulings in the Decisions Log, or delete a rule because it is long.
