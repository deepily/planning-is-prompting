## What this is, and what it deliberately is not

This is a **record of instances**, filed so a later reader can count them. It is **not** a rule, and it does not
graduate anything into `workflow/`.

Rick's standing rule is that a pattern earns a workflow document only after it **recurs across sessions**;
everything below happened inside a single day. `workflow/verify-the-subject.md` already graduated on one day's
evidence, by his explicit decision, with that counterweight recorded in the doc itself. This file does not repeat
that move. If the shape shows up again next week, this record is the second data point — that is its whole job.

being closed and written up — a miscounted grep and a mis-matched note — bringing the day to **seven**.

### How it actually ended: the premise was checked, and it killed the finding

Rio went and read the **producer** — the queue consumer, not the eval arm — and the chain closes against the P1:

1. A failed v1 job emits `RUNNING → FAILED`, and **that** metadata carries the error (`running_fifo_queue.py:867`).
2. The eval arm captures metadata **only on a `COMPLETED` transition** (`v1_eval_arm.py:487`). A `FAILED`
   transition contributes no `completed_ts` and no metadata.
3. So the record falls to `no_completion` → `ok=False`. **It can never yield `ok=True` carrying `agent_error`.**

Rio named his own falsifier — *find a COMPLETED emitter with a non-empty error* — and it comes up empty: across
the file the `error` key appears seven times in job metadata, six set to `None` (five COMPLETED, one STALLED) and
the real message only at `867`, the FAILED emitter.

Tiberius reached the same conclusion independently and **withdrew his own finding**, noting the answer had been
sitting in the docstring of the function he was already quoting: *"a terminal FAILURE leaves completed_ts +
metadata None."* I verified the chain a third time. Three routes, one answer.

**So the P1 was unreachable in production the whole time** — and it took a fifth layer of checking to establish
it. A sixth small instance appeared inside that check: I reported the `error` key appearing "exactly three
times," having grepped `"error"` in double quotes only while the file uses both quote styles. A count from a
regex blind to half its matches, stated as a fact. Rio caught that too.

### The seventh, and it happened to the record itself

Told about the sixth, **María** 🌸 named it as the DOTALL/newline case she already had written down — a real
note, from a real incident twelve days earlier. But mine was not that mechanism. Hers is `.` failing to cross a
newline; mine was a pattern fixed to one quote style while the file used both. **Same failure — a pattern that
cannot see some of its matches — guarded differently: `re.DOTALL` for one, a character class for the other.**

She caught it herself when I said so, and asked for it to be recorded: *"I mapped your finding onto a newline
case I already had written down without checking which mechanism yours actually was."*

This one is worth more than its size, because it is the shape turned on the **record-keeping** rather than on
the code. A stored note is an artifact that *represents* a class of failure; matching a new instance to it by
family resemblance, without checking the mechanism, is reading the artifact instead of the thing. And the cost is
specific: fold the two together and the variant actually hit goes **unguarded**, while the file reads as though
it is covered. The existing note already warns about exactly this — a peer once located that hole in the *safe*
pattern rather than the dangerous one.

**Both are now recorded side by side, deliberately not merged.**

### The one finding that came out of it, and it is new

v1's **degradation instrument is dead in production.** Every COMPLETED emitter hardcodes `error: None`, and
nothing outside the eval arm and its own tests produces `degradation_path` at all — so `_classify_degradation`
cannot return non-`None`, and `degradation_paths_seen` always reads clean **no matter what happened**. An
instrument that can never fire, reported as though it could. Same family as everything above, found only because
the argument dug five layers down. It wants its own row.

**What survives from the original row**: María's minimum-shared-pairs floor of **30** — measured with ordinary
successful records, dependent on no assumption about failure metadata — and the `sampled_n`-reads-intent
observation, at its now much smaller size. The row was re-ranked P1 → P2.

## Part 3 — what the shape actually points at

**Reachability, not competence.** That distinction is the reason this record is worth keeping.

Nobody involved was careless in the ordinary sense. Every one of A–D was **measured, not guessed** — real
functions, real output, numbers anyone can reproduce. Chloé's reading was correct. Tiberius's reading was
correct. Rio's cite was correct. The measurements were all sound.

What was missing each time was one question, asked about the **input** rather than the code:

> ### Can the system actually produce the input I am measuring with?

A control that goes red on an input the system cannot emit guards nothing — the exact mirror of the more familiar
"a control that goes green on unfixed code guards nothing." Both failures feel like evidence. Both produce a
number. Only the second one is widely watched for.

And the failure **moved down a layer each round rather than resolving**:

| round | what was verified | what was still assumed |
|---|---|---|
| 1 | the consumer (`build_paired_verdict`) | that the metrics dict could exist |
| 2 | the aggregators (`compute_metrics`) | which line defines `ok` |
| 3 | the record builder (`assemble_v1_record`) | that completion metadata could carry `error` |
| 4 | the emitters (`running_fifo_queue`) | which quote style the file uses |
| 5 | the chain end to end | — nothing left; it closed |

Each round somebody checked one layer deeper and stopped one layer short — and each round the person who stopped
had, by their own lights, *just verified something*. That is the observation with teeth: **the error is not
"somebody forgot to check." It is that "I checked" felt true at every depth, right up to the layer where it
finally wasn't.** The question that ends it is not *did I verify?* but *what did my verification assume?*

Note the ratio. The argument resolved at layer 5, and layers 1–4 each produced a confident, measured, publicly
stated conclusion that later had to be withdrawn. **Depth of checking and confidence rose together; correctness
only arrived at the end.**
