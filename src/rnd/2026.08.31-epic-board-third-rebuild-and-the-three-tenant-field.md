## 🔴 The finding that outlives the stamping

**`correlation_key` has three tenants, and only one of them is an epic.**

| Tenant | Rows | Written by |
|---|---|---|
| `epic:<slug>` | 191 | humans, deliberately |
| `cascade-<run>` and other free-form | 289 | cascade runs, historical |
| `cc-task:<sid>:g<gen>:<id>` | 52 | **the harness mirror, automatically** — as an idempotency upsert key |

This was **measured first by Maya 🌻 on 2026-08-30** and sits in row `5246bb67`'s body. I re-derived
it today from the other end and initially wrote it up as an independent confirmation; it was not, and
that claim is corrected on the row. Two readers of one source is not corroboration.

**Why it matters right now**: Rick ruled *reject-on-creation* today. The obvious implementation tests
`correlation_key != ""`, and **that predicate is inert on two of the three lanes** — it cannot
distinguish a considered `epic:seal-the-test-tier` from an auto-stamped `cc-task:8982f548…:7`. A row
can pass the guard while carrying no epic at all, and the board then reads as covered *because* the
check passed.

⇒ The predicate has to be `startswith("epic:")`, with the mirror's lane exempted or taught to stamp
`epic:unassigned` alongside its machine key.

⇒ **And Maya's own recommendation contradicts the ruling**: a *detector* over the rows, not a guard on
the doors, because *"a creation-time guard on a three-tenant field buys the appearance of a covered
field."* Rick ruled without that in front of him — my ask carried the 08-29 framing and not her
08-30 amendment. **The ruling stands; he is owed the chance to rule again with the evidence.**

## Method, for whoever re-derives this

Two instrument errors happened during this pass and both are the same shape — *an instrument answering
a narrower question than it appears to*:

1. **`include_parked` is not a server parameter.** The MCP verb accepts it and translates it to
   `hide_parked=false`; the raw API silently ignores `include_parked`. My first raw pull returned **15
   rows against the MCP's 35** and I nearly worked from it.
2. **The whole-board query needs `unscoped_audit=true` and paging.** Without it the result is capped
   and reads as a complete board.

🔴 **Neither of these is new, and that is the actual finding.** The 2026-08-29 pass — my own — closes
on exactly this: *"the MCP verb and the REST route spell the parked switch differently … so an audit
written in the MCP verb's vocabulary and run over HTTP describes eleven rows, calls it eighteen, and
prints a plausible `total 2174` right beside it."* **I documented the trap, then walked into it two
days later**, and only caught it because 15 and 35 were too far apart to ignore. A number that had
landed at 33 instead of 34 would have passed.

⇒ **Writing the lesson down did not install it.** The 08-29 entry ends by naming a detector as the fix
and none was built, so the only thing standing between this pass and a wrong number was my noticing.
That is the same argument Maya makes about creation-time guards one section up, and the same one this
repo's `CLAUDE.md` makes about rules that depend on remembering. **Three sightings now.**

The canonical form, from `lupin/src/scripts/scan-prose-task-refs.py`:

```
include_terminal=true&unscoped_audit=true&hide_parked=false&limit=200&offset=<n>
```

⚠️ **The trap Maya flagged and I second**: the API key lives in gitignored `src/conf/keys/**`, so it is
**absent from every worktree**. `read_api_key()` degrades to `""`, the store 401s, and a naive audit
reads that as an **empty board that audits clean**.
