## Why it is not showing: `created_by` is not in the terse projection

`task_query(terse=True)` returns id / title / status / blocked_by / next_chase_ts / priority /
`park_reason_stale`. **`created_by` is not among them.** The full row carries it; the at-a-glance
projection the board reads does not.

⇒ **The change is two edits, not one**: add `created_by` to the terse projection, then render it.
Rendering alone will show blanks, because the board never receives the field.

---

## 🔴 The parsing trap — 6 of 13 rows render wrong under the obvious implementation

`created_by` is `"<persona> <sid8>"`, and **"mr radio" is a two-word persona.** So:

```python
created_by.split()[ 0 ]          # -> "mr"      ✗ on 6 of 13 live rows (46%)
```

```python
PERSONA_AND_SID = re.compile( r"^(?P<persona>.+?)\s+(?P<sid>[0-9a-f]{8})$" )
m = PERSONA_AND_SID.match( created_by )
persona = m.group( "persona" ) if m else created_by      # -> "mr radio"   ✓ 13 of 13
```

Verified: all 13 live rows match that pattern; the naive split disagrees with it on exactly the
six "mr radio" rows — **which are the same six rows Rick asked about.** The obvious implementation
fails hardest precisely where he needs it.

⚠️ **Fall back to the whole string, never to a slice.** A non-matching `created_by` should render
verbatim rather than be cut at the first space — an unparseable value shown whole is legible; one
truncated to its first token is a wrong name presented as a right one.

## Two smaller things the measurement turned up

**1. Persona case is not normalised.** Live rows carry `Krishna` and `Tiberius` capitalised while
`maria`, `mr radio`, `maya`, `john` are lowercase. Display-casing them in the UI keeps the stored
values untouched and avoids a migration nobody asked for.

**2. Filer and owner are usually but not always the same.** Three of the 13 differ — maya filed a
row María owns, maya filed one Mr Radio owns, john filed one Mr Radio owns. So the field is worth
showing *beside* the owner, not instead of it; a single "who" column would silently merge two
different questions.

---

## Recommendation

Show it on **every** ticket per Rick's general rule, as a small secondary line under the title —
`filed by <persona>` — with the owner kept where it is. On the waiting-on-Rick group it answers his
question directly; everywhere else it is one short line that costs a row nothing.

## Method note, and a correction to my own first pass

My first sweep of this reported **"19 rows, 0 missing"**. That number was wrong, and the way it was
wrong is worth recording because the endpoint told me and I did not listen.

`GET /api/tasks` returned `truncated: true`, `has_more: true`, and a `warnings` array saying
*"response truncated at the 100000-char budget — 3 of 4 matching rows serialized"*. My script read
`tasks` and ignored `warnings`, so a truncated page became a census, and the "19" silently mixed
non-terminal rows with seven `done` ones.

⇒ Corrected by re-querying per status with `terse=true` and checking `truncated` / `has_more` on
every response. **The live board is 13 rows, not 19.** A payload that reports its own truncation is
only as good as the field nobody reads.
