## 1. The time math — cascaded vs serialized

### 1.1 The formula (canonical statement)

`workflow/plan-review-cascaded-parallelism.md:23`, verbatim:

> **The compression**: for an N-section plan with 3 review stages, serial wall-clock is `N × 3 × per-cell-time`. Section-pipelined wall-clock is `(N + 3 − 1) × per-cell-time` — `N+2` cells in the critical path instead of `3N`.

Worked instance (`:25`): **N=4 sections at 15 min per cell: serial = 180 min; pipelined = 90 min. 2× speedup at the limit.**

The general form (any stage count) appears in `src/rnd/2026.05.22-run-5-serial-vs-parallel-root-cause.md:57`: total wall-clock ≈ **`sections + stages − 1`** cells. The formula is independently restated in the executive briefing `src/rnd/executive-briefings/2026.06.08-a-good-plan-via-cascaded-review.md:68-71`.

Per-cell derivation (`parallelism.md:61-65`): ~10 min reviewer work + ~5 min author revision = 15 min/cell, with author revisions overlapping the next stage so the critical-path math holds.

### 1.2 Why it works (the mechanism, for the blog's explainer paragraph)

- `parallelism.md:13`: "Section-pipelining is the lever… At steady state, **all three reviewers are busy on different sections of the same cascade concurrently**." Steady-state window shown in the time-slice table at `:67-102`.
- Original design statement, `src/rnd/2026.05.17-cascaded-plan-review-pipeline.md:27`: "while section A is being reviewed by the usability reviewer, the author can start section B… — **pipelined throughput on a constant per-section latency**."
- Bottleneck rule: "the slowest section is the pipeline bottleneck" (`workflow/plan-review-cascaded-input-spec.md:38`, elaborated `:94`).
- The OLD process explicitly forbade this: `workflow/plan-review.md:55` — "**Strictly sequential — never parallel**… If a competent-but-impatient agent thinks it can save wall-clock time by parallelizing, the answer is no." (Great before/after contrast for the post.)

### 1.3 The negative proof — Run 5 ran serial by accident and lost the dividend

`src/rnd/2026.05.22-run-5-serial-vs-parallel-root-cause.md` is an entire root-cause doc on this: Run 5 ran pass-serial (`:16`), stage durations were **44 / 44 / 25 min with only one reviewer ever active while the other two sat idle** (`:61`), and pass-barriers made pipelining "impossible **by construction**" (`:103`). Compare Run 4's pipelined 38→33→21 min stages (pipeline doc `:818-826`). Nothing sells a formula like the run that violated it.

## 3. The virtuous circle — post-game feedback wired back into the process

Nine complete lesson→codification pairs were found; the five below both removed operator involvement AND have receipts on each side. (Full list in the evidence appendix, §5.)

### 3.1 The ~4-hour rubber-stamp → gate deleted (the flagship)
- **Observed** (notif-sync post-game `:37`): "The cascade parked at Step 3 for **~4 hours** waiting on the user's explicit decomposition approval… The user gate was a rubber-stamp on an already-validated decision." A mandatory gate at every boundary "would multiply the waste by **~12×**" (`:53`). Rick's own words, same doc `:51`: "**I should not be a gate at any point between the start and finish of the three review phases.**" Corroborated by Run 5's PG-10 (`run-5 post-game :128`): three gates fired; two carried zero decisions — Rick: "why twice have I been asked to explicitly approve the end of a pass that did not have significant need for approval."
- **Codified**: Step 3 is now **cast-ratified-conditional** (`workflow/plan-review-cascaded.md:125`), with the config default anchored to this exact incident (`plan-review-cascaded-defaults.md:156`) plus the no-inter-stage-gate rule (`plan-review-cascaded.md:223`); Decisions-Log ruling at `TODO.md:133`.

### 3.2 "Buried the lead" → proactive decision-delivery (meta-rule 6) — paid off the same night
- **Observed** (`src/rnd/2026.07.01-cascade-proactive-decision-delivery.md:13-15`): the Manager parked user-destined decisions behind "do you want to review?" softness. Rick: "takes the findings and puts them in front of my face for review **without asking if I want to review them**."
- **Codified**: Manager System Prompt meta-rule 6, applied across 5 workflow surfaces (`workflow/plan-review-cascaded-common.md:193` and siblings; version-history receipt `plan-review-cascaded-personas.md:584`).
- **Next-run payoff, same night**: the filter half was applied to the GCP cascade hours later — settled items filtered off Rick's desk, only the genuine cost question surfaced, producing the **$527/mo win** (steward post-game `:25`, `:60`). This is the cleanest N→N+1 loop on record.

### 3.3 User-as-moderator → Steward-moderated post-game (the retro itself de-operator-ized)
- **Observed**: in the 2026-06-29 fleet retro Rick accidentally became the moderator — "participants only relayed the same comments to me… Not sustainable" (`src/rnd/2026.06.30-post-game-self-driving-moderation.md:5`, `:24`).
- **Codified**: `workflow/post-game.md:76-78` — the post-game "is a **conversation the Steward moderates**… **the user is the audience, never the moderator or the relay**."
- **Payoff**: first live moderated roundtable ran the next session with 4 contributions (`TODO.md:3`).

### 3.4 Ad-hoc excellence → required stages (Step 9 and Step 0)
The Manager improvised **1,225 LOC** of post-cascade synthesis in Run 3 and a **~1500-word** preparation brief in Run 4; both were codified as required Steps 9 and 0 for every subsequent run (`workflow/plan-review-cascaded-defaults.md:105`, `:111`). Run N's improvisation became Run N+1's guarantee.

### 3.5 The retro role was itself born from a retro (the meta-loop)
The post-Run-4 María↔Tiberius retrospective promoted **7 workflow extensions** in one fold — including creating the **Observer/Steward persona and probe protocol** (`plan-review-cascaded-common.md:966`; `plan-review-cascaded-personas.md:586`). The personas doc now describes the Observer as "the **meta-engine of the cascade's self-improving property**" (`:67`). The role that harvests the lessons exists because a lesson said it should.

### 3.6 The honesty guardrail (worth a paragraph in the blog)
Not every lesson graduates. Two are deliberately parked pending recurrence — drive-vs-hold miscalibration ("wait for a larger cross-session pattern," fleet retro `:58`) and a server-side-pass reviewer rubric (`TODO.md:86`). The circle stays virtuous because single anecdotes don't rewrite doctrine.

Also fold in the cascade-learning loop INSIDE a run: Stage-2 finding counts compressed **6 → 8 → 4 → 8** across sections as reviewers carried patterns forward, with Section D down **~50%** vs Section A (`plan-review-cascaded-common.md:875-883`); Run 4's stage times decayed **38→33→21 min** (pipeline doc `:818-826`) — the same learning dynamic, measured two ways.

## 6. Honesty ledger — what is modeled, assumed, or absent (do not overclaim in the blog)

1. **The 180-min "serial" figure is modeled, not stopwatch-measured** — `N × 3 × 15 min`; no serial `/plan-review` was ever run on the same plan as a controlled baseline (it was listed as planned telemetry, pipeline doc `:257`, and never executed). The measured "before" anchor is the **4–5 hr estimate** of the pre-pipeline single-AI workflow (exec summary `:49-57`) — an estimate, label it as such.
2. **15 min/cell is an explicit assumption** ("assume each cell costs…", `parallelism.md:61`), not telemetry. Measured stage times exist per-stage (38/33/21; 44/44/25), not per-cell.
3. **The 2× speedup is asymptotic** ("at the limit"); no doc quantifies small-N speedup where ramp-up/ramp-down dominate.
4. **No wall-clock recorded** for the mux-MVP-finish, GCP, and mux-consolidation cascades; GCP has no total-findings count beyond "10 Arnold findings"; Run 1 was abandoned (3 foundational findings + 11 lessons, no clean telemetry).
5. **The cascade has been factually wrong**: 2 cascade facts were overturned by Rick in the mux-MVP run (a legacy sub-icon and an endpoint both existed despite reviewers' greps saying otherwise — decisions stood, factual basis wrong; observer-retro `:27`). A server-side-pass rubric is parked awaiting recurrence. Including this makes the 37× claim credible.
6. **Vocabulary note**: no run reports "review cycles / contested" style metrics; the corpus's native metrics are findings, user-touches, escalations, re-litigation rounds, and votes called. Quote in those terms.
7. Some receipts live in `io/post-games/` which is **untracked by design** (post-game corpus ruling, 2026-06-30) — cite them in the blog as internal retro records, not linkable repo files.
