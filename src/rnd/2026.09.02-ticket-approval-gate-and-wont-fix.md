## What Rick asked for

> "I want a delete button to summarily dismiss them without any record keeping... by closing it as
> 'won't fix'. Sound familiar? I also want an approved/not approved status for any new tickets,
> that either only managers or me can approve and put into the active mix. I want a holding area so
> we can absolutely separate the wheat from the chaff and prioritize as a group what should be
> worked on and what should be summarily closed as 'won't fix'."

Three features, and they are not independent:

1. **Won't-fix** — a terminal close that takes a row off his board immediately.
2. **Not-approved by default** — a new ticket is invisible to everyone until approved.
3. **A holding area** — where unapproved tickets wait to be triaged as a group.

Yes, it is familiar: this is ordinary issue-tracker triage — an inbox, a grooming session, and a
`wontfix` close. What follows is what changes when that pattern meets *this* store.

---

## 🔴 The one implication that decides whether this works

**Won't-fix must NOT count as a close in the ratio gate — and the reason is Rick's own.**

He already ruled, on the ratio gate (2026-09-01, eight rulings): the numerator is `done` **only**,
and `dropped` is excluded, *because counting a drop lets you mint a ticket by deleting one*.

A won't-fix close is a drop wearing a different word. If it counted:

```
close 3 as "bullshit"  ->  earn 3 new ticket slots  ->  file 3 more
```

⇒ **The summary-delete button becomes an infinite ticket generator, and the gate reads green while
the board grows.** The precedent already settles it: `wont_fix` joins `dropped` on the excluded
side of the ratio. No new decision needed — just don't lose it in implementation.

---

## 🔴 The reframe that makes the two features help each other instead of fight

The gate meters **created ÷ closed**. So: does a ticket in the holding area count as *created*?

| If a submission counts as created | If only an APPROVAL counts as created |
|---|---|
| The gate throttles the **holding area** — the one place free capture is the whole point | Capture stays free; the gate meters what actually reaches the board |
| A worker who spots a defect mid-task is refused, so the finding goes in a DM and is lost | The finding is always captured; approval decides whether it becomes work |
| Two controls fighting over the same event | Rate control and quality control on different events |

**Recommendation: the gate meters APPROVALS, not submissions.**

This keeps the asymmetry argument Rick made — *"way too easy to add, way too hard to remove"* —
because the expensive-to-reverse act is putting a row on someone's board, not writing one down.
It also makes the holding area do the job the moratorium is doing today by brute force.

⇒ **This feature retires the ticket moratorium.** The moratorium is a blunt rate limiter standing
in for a quality gate that does not exist yet. Once submissions land in a holding area instead of
on the board, there is nothing left for it to protect against, and it can be lifted permanently
rather than re-declared.

---

## "Without any record keeping" — what he wants, and what I would not do

Two readings, and they differ a lot in cost:

**(a) Hard delete — the row's bytes are gone.**
Against it: the store's transition log is what this fleet reconstructs history from, and every
"who filed this / when did it change" question — *including the attribution Rick asked for in this
same message* — reads that log. A purge path would be the one operation that can destroy evidence,
and it would be reachable by anyone with the API key.

**(b) Won't-fix — terminal status, row retained, off every board and every query.**
This delivers what he actually described: one click, gone from his view, no curation, never seen
again. He is not asking to run forensics on rejected tickets; he is asking not to look at them.

**Recommendation: (b).** If a hard delete is genuinely wanted later, it should be a separate,
audited, admin-only purge — not the same button as the triage close.

⚠️ **One deliberate exception to "no record keeping": keep an optional one-line reason.** Rick's own
ask in the same breath was *"I don't know who to attribute it to to track it down."* **Who filed it
+ why we killed it** is exactly the pair that answers a repeat offender. Optional, one line, never
a required field — a mandatory justification box is how a fast button becomes a slow one.

---

## What `not_approved` breaks if it is added carelessly

A new pre-queued state is not just another enum value. Everything that reads the board has to learn
about it, and the failure is silent in the worst direction — **workers inheriting work nobody
approved.**

| Reader | What happens if it does not exclude `not_approved` |
|---|---|
| The owed-work oracle (Stop hook) | A session is told it owes work nobody approved — the heartbeat pokes about phantom obligations |
| `task_query( owner_persona=me )` | Unapproved rows appear on a worker's board and get worked |
| The Epic Board / Task List | The holding area leaks into the live view, which defeats the feature |
| The `Live:` count in the header | Inflated by rows that are not live |
| Manager context ticks | Managers chase rows that were never approved |

⇒ **Exclusion must be the DEFAULT in the query layer, not a filter each caller remembers to pass.**
A rule every caller has to remember is not installed. The safer shape: `not_approved` is excluded
unless a caller explicitly asks for the holding area.

**Grandfathering**: the 13 currently-live rows become `approved` — they are already on boards and
being worked. A migration that dropped them into the holding area would empty every board at once.

---

## Who can approve — and where the check has to live

Rick said *"only managers or me."* Two things follow.

**1. There is no role model in the store today.** Rows carry `owner_persona` and
`accountable_manager`, which describe assignment, not authority. So approval needs either an
explicit allowlist of approver personas, or a `manager` flag on personas. The allowlist is smaller
and is honest about being a policy rather than an inferred property.

**2. 🔴 A check that lives only in the UI is not a gate.** The store is reachable over
`:7999` with an API key that every hook-writing session already holds. If approval is enforced by
hiding a button, any worker can approve its own ticket with one HTTP call — and the ones most
motivated to do so are exactly the ones the gate exists to stop. **The check has to be server-side,
on the transition, and it has to reject rather than warn.**

⚠️ **And it needs a test that tries to self-approve as a non-approver and watches it fail.** An
authorization check nobody has watched refuse is not a control; the whole point of this row is that
this fleet keeps finding assertions that never went red.

---

## The group triage session

*"Prioritize as a group what should be worked on and what should be summarily closed"* implies a
batch view, not one-at-a-time review:

- The holding area as its own list, sorted **by filer** — that is the view that makes a pattern of
  low-quality submissions visible, which is the attribution Rick asked for.
- Batch approve / batch won't-fix, because a triage session that takes one click per ticket will
  not happen twice.
- A per-filer tally: **approved vs won't-fixed**. This is the actual answer to *"who's posting
  ridiculous things"* — a name on one bad ticket is an anecdote; a ratio across twenty is a signal.

This is cheap once `created_by` is displayed, which is already specced
([filer attribution](2026.09.02-epic-board-filer-attribution.md), commit `cdae439`) and already
measured as display-only with no backfill.

## `bc77cd79`, the row he named

He called it a ticket that *"never should have been allowed in the first place."* Worth being
accurate about what it is, because it shapes what the holding area should catch.

It is the **moratorium record itself** — Mr Radio's row saying no new workers and no new tickets
until Rick's word. It was not a work item; it was a policy note written as a row, deliberately,
because *"a constraint that lives only in this context window dies at the next `/clear`."*

⇒ **The reasoning was sound and the artifact was still wrong for the board.** A policy that
everyone must read is not a task anyone can finish, so it sat on the live board with no terminal
state, accumulating chase timestamps and reading as work owed. That is the shape to catch: **rows

⇒ A holding area alone would not have caught it — it would have been approved, because it was
genuinely important. What catches it is a **separate kind**: a policy/notice item that never
appears in owed-work counts, or a required "what does done look like?" field at submission, which a
policy note cannot answer.

**Recommendation**: add that question to the submission form. It is one line, it is answerable in
five seconds for real work, and it is unanswerable for exactly the class Rick is objecting to.

## The measured vocabulary

`src/cosa/rest/task_store_rules.py:38-39`

```python
VALID_STATUSES    = ( "queued", "claimed", "in_progress", "blocked", "parked", "review", "done", "dropped" )
TERMINAL_STATUSES = ( "done", "dropped" )
```

`src/cosa/rest/task_store_owed.py:128`

```python
OWED_BASE_STATUSES = ( "queued", "in_progress" )
```

## The split, and it decides the implementation

| Reader | Shape | A new `not_approved` status would… |
|---|---|---|
| Owed-work oracle — `OWED_BASE_STATUSES` | **allowlist** (names what IS owed) | **not leak.** Safe by construction. |
| `task_repository._apply_owed_filter:1025` and `:1032` — `status.notin_( TERMINAL_STATUSES )` | **denylist** (names what is hidden) | **leak.** Included in every un-status'd query. |
| The unscoped-query guard's count — `count_tasks( include_terminal=False )` at `:898` | denylist, same filter | **inflate**, and it feeds the threshold that rejects broad pulls |

⇒ **My warning was aimed at the wrong reader.** The owed oracle — the one I named first and worried
most about, because a worker inheriting unapproved work is the worst outcome — is already immune,
because it enumerates what is owed rather than subtracting what is not. The leak is in the general
list query, which is what paints the board and what the `Live:` count is derived from.

## Which gives each feature a different implementation cost

**Won't-fix is nearly free, and this is a real argument for making it a STATUS rather than a flag.**
It is terminal by nature, so adding it to `TERMINAL_STATUSES` propagates to **every denylist reader
at once** — the board, the counts, the guard, the prose-refs check. One tuple, and it disappears
from all of them. A boolean flag beside `status` would instead need every one of those call sites
edited by hand, which is the same class of "a rule each caller must remember" this fleet keeps
getting bitten by.

⚠️ And it stays out of the ratio numerator **by construction, not by discipline** — the gate counts
`done` only (Rick's ruling), so a new terminal status is excluded unless somebody deliberately adds
it. The infinite-ticket-generator risk in §1 above is real but it is a *don't-do-this*, not a
*must-remember-to-exclude*.

**`not_approved` is the expensive half**, precisely because it is NOT terminal. It needs a third
set — the statuses that exist but do not appear on boards — and both denylist filters have to
consult it. Adding it to `TERMINAL_STATUSES` to get the hiding for free would be wrong: terminal
carries other meanings here (`blocker_is_terminal`, the rejoin logic at
`task_store_rejoin.py:205`, `post_terminal` at `task_repository.py:741`), and an unapproved row is
not a finished one.

## The guard this codebase would want

There is already a precedent worth copying. `task_store_owed.py` asserts, **at import**, that
`PARK_LEGAL_FROM_STATUSES ⊆ OWED_BASE_STATUSES`, with a comment explaining that without it "nothing
else would fail: both twins still agree, every existing test still passes, and the fleet quietly
starts getting poked about rows it never was before."

⇒ The same shape applies here: **assert at import that `not_approved` is not in
`OWED_BASE_STATUSES`.** A silent widening of the owed set is exactly the failure that comment
describes, and this codebase has already decided that the place to catch it is import time rather
than a test somebody might not write.

  of this design is still described from behaviour.
- No test was run. Every claim above is from reading, and the line numbers are from today's HEAD.

## Two rulings, not one

**And an unasked requirement**: `approved → not_approved` must be legal. A row already on the live
board can be **demoted back to the holding area**, not only killed.

## 🔴 Demotion is the reversible sibling of won't-fix, and it strengthens §3

§3 argued against a hard delete because it destroys the attribution trail. Rick has now supplied
the reason that argument was incomplete: he wants a **non-destructive** way to get something off his
board. Won't-fix kills; demotion returns it to triage.

⇒ **Together these are a complete pair, and neither needs a delete.** "Get it off my board" is now
answerable two ways, and only one of them is terminal. That closes the hard-delete question rather
than merely arguing it.

## What the store has to grow

| Transition | Kind | Notes |
|---|---|---|
| `not_approved → queued` | promotion | gate 2 — either approver |
| `not_approved → wont_fix` | terminal | triage rejection |
| `queued/… → wont_fix` | terminal | kill a live row |
| **`queued/… → not_approved`** | **demotion — NEW** | the one he just added |

⚠️ **The store's transitions are constrained, not free.** `task_store_rules.py` carries explicit
legality sets (`PARK_LEGAL_FROM_STATUSES`, and an import-time assert coupling it to the owed set).
So demotion is not "allow anything"; it needs its own legality entry and its own reason.

## 🔴 The risk this creates, and it is the one my §"not established" section already flagged

I wrote, unresolved: *"whether `not_approved` should expire. A holding area with no eviction policy
becomes its own unbounded list — the exact asymmetry this is meant to fix, moved one room over."*

**Demotion makes that worse, because the holding area now fills from BOTH directions** — new
submissions in the front, demoted rows in the back. Without an eviction policy a row can cycle
indefinitely: promoted, demoted, promoted, never worked and never killed, and never counted as
anything.

⇒ The store already has the shape of an answer. `parked` means *a human ruled this not-now*, and it
is **bounded and self-expiring** — the chase timestamp re-admits it automatically at read time,
with the explicit rule that an indefinite hold is not a park, it is a `dropped` with a reason.

⇒ **Recommendation: give `not_approved` a chase the way `parked` has one.** A row demoted to the
holding area resurfaces for triage after N days rather than resting there. That reuses a mechanism
this fleet has already debugged, and it keeps the holding area from becoming the thing it exists to
prevent.

## Two smaller consequences

**1. A demoted row must not re-count as `created` when re-promoted.** `created_ts` is immutable and
the ratio window rolls it off, so this is probably free — but a re-promotion that stamped a new
creation event would double-count one ticket and choke the gate on its own bookkeeping.

**2. "For now" is doing work in his answer.** Either-suffices is explicitly provisional. Worth
