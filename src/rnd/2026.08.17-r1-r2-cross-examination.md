## Why this exists

The overnight post-game (`§8`) drafted two stale-read rules, R-1 and R-2, on twelve provenance-carrying deposits across six seats and two repos. `post-game.md` §5.3 forbids graduating a rule without cross-examining the seat that produced it — and **every source was reaped before the harvest except Cheech**, who is live. This closes that gate.

**R-1 (as drafted)**: *"Re-measure at send-time and stamp the window. Any blocker, verdict, or gap report against a tree under active edit states the tree-state it was taken against (commit SHA / git status clean / container / running process) and is re-measured immediately before sending."*

**R-2 (as drafted)**: *"'Verify on disk' must name WHICH disk state. Committed · working-tree · container · running-process are four different worlds. A verdict turning on committed-vs-uncommitted runs against `git show HEAD:` or a clean tree, and checks `git status` first."*

## The instance examined

Cheech's **#13**, the live same-day recurrence (post-game §3.1): he flipped the worker-model INI keys, 171 unit tests went green, a fresh Python resolve returned `claude-opus-5` — but his own live MCP dry-run still printed `claude-opus-4-8`. Diagnosis: one `cosa_voice_mcp.py` per Claude Code process, `ConfigurationManager` a singleton with no mtime check, so every live session holds its own stale INI snapshot and only NEW sessions read the flip. **The file was right and every running process was stale.**

## Cheech's testimony (verbatim; corrections read back before recording)

*Provenance note: his words come from the DM channel, which stamps "condensed in transit." The two load-bearing formulations and the verdict line were read back to him and confirmed or corrected before recording — attributing a paraphrase as verbatim would itself be the subject-misplacement this record is about.*

**Verdict** — *"R-1 would NOT have caught my instance, and R-2 only makes it detectable, not caught."*

**On R-1** — *"I DID re-measure at send-time and the measurement was correct — a fresh process resolved the four keys right and I said so; the defect was measuring one subject (disk) and reporting a conclusion about another (what a live spawn would do), so freshness was never the broken axis. Mine was not stale, it was MISPLACED."*

**On R-2** — *"R-2 gets closer by forcing me to name the state, but it fires only if the reader notices the named state isn't the one the claim needs — and it carries a category error worth fixing before you graduate it: a running process is NOT a disk state; its memory can differ from every disk state at once and nothing on disk can reveal that."*

**The reframing (the part that decides graduation):**

- **The class splits into two failure modes** — *"Two failure modes hide under 'stale read' — TIME (a correct read of the right subject, taken too early: Maya's no-auto-reload, the doc cases) and SUBJECT (a correct, fresh read of the wrong thing: mine)."* Corrected on read-back: *"TIME and SUBJECT are not mutually exclusive in claims … each instance should be labeled based on its dependency."*
- **In-memory state is its own subject, not a disk state** — it has *"three properties no disk state has: it can differ from every disk state at once, it is unobservable without asking the process, and it changes only at process boundaries (boot/bounce/reload)"* — which he then **narrowed himself**: *"'changes only at process boundaries, not on write' is true for cache-on-first-use processes but not for others like TTL or watcher processes. The correct form is: 'the refresh schedule belongs to the process, not to the writer.'"*

## What this means for graduation (Krishna's read for María — not a rule edit)

1. **R-1 is UNDERCUT for its own founding instance.** It targets freshness (the TIME axis); Cheech's read was fresh and correct and failed on the SUBJECT axis. A rule that would not have caught the instance cited to justify it is not ready as drafted.
2. **R-2 is detectable-not-caught and mis-taxonomised.** It relies on the reader noticing a mismatch (no mechanism), and it lists running-process as a fourth "disk state" — the category error Cheech names.
3. **The amendment his testimony points to** (for Rick to weigh, via María): split the rule along **TIME** (re-measure at send-time — R-1's real scope) vs **SUBJECT** (verify the subject of the claim is the one it depends on, not an adjacent one); treat **in-memory / running-process state as a distinct subject**, not a disk state, whose *"refresh schedule belongs to the process, not the writer,"* so a claim about live behavior must probe the live process because nothing on disk reveals it.

⇒ **The founding instance falsifies R-1 on its own terms.** That is a more valuable result than a confirmation, and it is why this went to a live source instead of graduating on volume alone.
