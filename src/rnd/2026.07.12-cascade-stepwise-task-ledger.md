## The idea (Rick's, 2026-07-12, voice)

> *"Add this recent idea I had about having the manager of a cascaded review mint an entire set, stepwise, of each of the passes or stages that a review has to go through before it's actually finished."*

The Manager of a cascade must put **the whole cascade on the board before it starts** — one task-store item per step it has to walk through — and keep those items current as it walks them.

## Why it matters (the problem it actually solves)

A cascade is the most opaque thing the fleet runs: hours long, five-plus sessions, and a DM/topic trail nobody outside it reads. Before this change, the user's only windows into a running cascade were:

1. the Manager's `notify()` pushes — which fire at **section close**, i.e. rarely; and
2. asking.

Between pushes, a cascade is a black box, and **"no news" is indistinguishable from "the Manager is a phantom."** Today, ~20 minutes into the `cascade-eval-first` run, Rick asked *"why have I not seen any reviewers spun up — or is she using subagents that are opaque to our eyes?"* That question is the symptom. The honest answer (cast assembly is Step 4; she was on Steps 0–2) was only reconstructible by a Steward pulling tmux, `ps`, `commons_who`, and the board. **The user should not need a Steward to answer "where is this thing right now."**

The ledger makes cascade progress **pull-able** instead of push-only. One query answers it:

```
task_query( correlation_key="cascade-<slug>", terse=True )
```

### The two tiers

| Tier | Minted | Granularity | Answers |
|---|---|---|---|
| **Step** | Step 0, before the cascade fires | one per step: 0, 1, 2, 3, 4, 5–6, 8, 9 | *Which step are we on?* |
| **Section** | Step 2 close, once decomposition ratifies | one per section (A, B, C, …) | *Is the pipeline actually moving?* |

Step 7 (Escalation) is a policy, not a work unit — it correctly gets **no** item.

**Both tiers are required.** The step tier alone is a checklist. A cascade that reports "on Step 5" for three hours has told the user nothing — pipelined section motion is this workflow's entire value proposition, so the board must show sections moving independently.

### Three required fields (this is where today's run was actually broken)

| Field | Why load-bearing |
|---|---|
| `correlation_key` (identical across the run) | Without it, nobody can pull the run **as a unit**. An item without it is invisible as cascade progress. |
| `accountable_manager` (non-null) | A null manager is an **unchaseable item** — the arbiter has nobody to poke when it stalls. |
| `body` = the step's acceptance criteria | Doubles as the Manager's rehydration crib after a `/clear`. |

### Status discipline

- `in_progress` when the step **starts**, not when it finishes. A cascade whose items flip straight to `done` has no observable middle.
- `blocked` + typed `blocked_by` + `next_chase_ts` — **this is how a stalled cascade announces itself.**
- `done` + `receipt_refs` — a step closed with no receipt is a rubber-stamp.

## Empirical anchor — `cascade-eval-first` (2026-07-12)

Manager Tiffany 💍 minted 8 step items **unprompted** — the practice was already latent in the fleet, which is the strongest argument that it belongs in the workflow rather than in one Manager's head. But:

- every item carried `correlation_key: null` and `accountable_manager: null` → the run could be neither pulled as a unit nor chased when stalled;
- there were **no section items** → the board could show *which step*, never *the pipeline moving*.

Rick's directive (USER BROADCAST `255b682f`) asked for a ledger *"we can track externally and see her progress as she runs the cascaded review through all of its stages"* — which the coarse step tier alone does not deliver. Hence: two tiers, three required fields, status discipline. Tiffany adopted all of it mid-run (run-config `265e854` §7: 8 step items + 4 section items, all correlated), so the mandate is **already validated once in flight**.

Standing practice is *don't graduate a single-session observation into workflow doctrine — wait for the pattern to recur* (memory: `feedback_accumulate_pattern_before_graduating_doctrine`). **This graduation is a direct user directive, which overrides that default.** Recording the deviation here rather than silently skipping it. Mitigating evidence that it isn't premature: the practice arose *independently* in the Manager (Tiffany minted the step tier with no instruction), and the gap it closes was surfaced *by the user in real time*, not inferred by me.

## Second change, same draft: the Capability-claim receipt rule

*Added the same session, from a live near-miss. Same approval gate — uncommitted until Rick's word.*

**The rule** (new subsection in `plan-review-cascaded-common.md` §Escalation Taxonomy): **an escalation abstract that asserts a CAPABILITY must cite the receipt proving that capability RUNS** — a port that answers, a process in `ps`, a resolved env var, a container's actual model list. Not that it is designed, specified, or illustrated in a document.

**Why it earns its place**: the user answers escalations *cold*, from a phone, on the strength of the abstract alone. A recommendation resting on a phantom capability spends his scarce attention ratifying a decision built on something that does not exist — and the error is **invisible to him by construction**.

**The trap, precisely**: a design document's *illustrative example* reads exactly like an *inventory*. "E.g. a locally served Qwen/DeepSeek judge alongside one or two API judges" describes a **desirable** panel; a reviewer under time pressure reads it as an **available** one. Those two sentences are indistinguishable at a glance.

**Empirical anchor** (`cascade-eval-first`, 2026-07-12): Stage-2 reviewer Rio's remediation for the judge-panel hole — *"add the local Qwen/DeepSeek judge per design-doc §9, so N≥3 survives with both exclusions"* — was escalated to Rick as decision `d8ec34d7`. The Steward checked the machine: **ollama not listening; no vLLM; the only local model server runs `nomic-embed` + `distil-whisper` — embeddings and ASR, no generative model at all.** The design doc's line was intent, never deployment. Rick was roughly one chase-cycle from ratifying a fix built on a capability that did not exist. **Cost of the catch: one port check.** Manager adopted it mid-run as run-rule **R7**; graduating it here.

**Relationship to standing memory**: this is the escalation-surface instance of `feedback_no_confabulated_results` (cite a primary artifact or mark it unverified) and of `feedback_verify_inherited_reference_before_surfacing` (reconcile-don't-dangle). Neither of those covered *the abstract of an escalation to the user*, which is the highest-stakes surface we have — hence codifying it where a Manager will actually read it.
