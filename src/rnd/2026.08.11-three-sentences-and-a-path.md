## Phase 1 — teach the workflows to say "three sentences and a path"

### 1.1 What changes, in one line

Today every canonical statement of the rule reads **headline + two supporting sentences**.
It becomes **headline + two supporting sentences + the path, when there is one**.

### 1.2 The wording that matters most

**The path is not a fourth sentence. It is a pointer, and it does not count against the three.**

This has to be said out loud in the rule itself, not left to inference. A rule that says
"three sentences" and then hands you a fourth line invites every reader — human or agent — to
score a compliant message as over the limit. The point of the path is to *replace* prose: send
the pointer instead of pasting the stack trace, the table, or the log.

Rick's framing, which is the "why" the docs should carry:

> "Our workflow that talks about DMs will absolutely direct agents to include a path to stack
> traces or other resources so as to cut down on the amount of tokens burned passing DMs back
> and forth."

So the rule reads roughly: *say it in three sentences; when the detail lives somewhere, send
the path instead of the detail. The path is not one of the three.*

### 1.3 Surfaces to change — all of them, or the rule is only half-installed

| # | file | what's there now |
|---|---|---|
| 1 | `workflow/brevity-mandate.md` **:16** | the canonical definition — *"Say it in Three Lines or Less: headline + two supporting sentences"* |

| 4 | `~/.claude/CLAUDE.md` | the 3LoL line, the banned-habits table, and the closing acronym table |
| 5 | `global/CLAUDE.md` (this repo) | verbatim snapshot of #4 — drifts silently if missed |
| 6 | `.claude/skills/brevity-mandate/SKILL.md` + `.claude/commands/plan-kiss.md` | what `/plan-kiss` and 😘 actually fire |

Six surfaces. #5 is the one that rots quietly, because nothing fails when it disagrees.

### 1.4 What this phase does NOT touch

- **No code.** `sentences.py` counts a bare path as a claim, which I raised at the wrong moment
  and in the wrong module. It is a real finding and it is **not** part of this phase; it belongs
  to whoever owns that gate, if and when the tutor path uses it.
- **No new acronym.** This extends 3LoL; it does not invent a sibling.
- **No change to the spoken/TTS rules.** A path is TTS-hostile and stays out of spoken text —
  that rule already exists and still holds.

### 1.5 One interaction worth knowing about

The `rejecting` arm refuses DMs over a word threshold. A path is one word however long it is, so
telling agents to add one costs essentially nothing against that gate. Live receipt from tonight:
my own handoff DM was refused (`dm_too_long`), and the rewrite that passed was exactly headline +
two supporting lines + a path.

## Phase 2 — the next experimental run

### 2.1 What is running right now

| | |
|---|---|
| block | `dm-verbosity-two-arm-v1-week2` |
| window | Tue 2026-08-11 15:00 → Sat 2026-08-15 14:00 EDT |
| slots | 56, **28 per arm** |
| arms | `blind` · `rejecting` (`dm_experiment.py:38`) |

`blind` = the judge grades the DM, the sender is told nothing. `rejecting` = over-threshold DMs
get an HTTP 413 refusal (`dm.py:802`).

### 2.2 Two constraints the existing code already sets

1. **A new treatment means a NEW block with its own id — never a relabelling.**
   `generate_schedule.py:99-102`: *"Adding it later means a NEW block with its own id, not a
   re-labelling of these slots, because a slot's arm is what its rows were collected under."*
2. **It cannot start before Sat 2026-08-15 14:00.** A DM can only be in one treatment at a time;
   overlapping blocks contaminate both.

### 2.3 The fork — how three treatments fit in two arms

Rick asked for the tutor **combined** with what's running, **as a two-arm test**. Three ways
to do that, and they answer different questions:

| | design | answers | cost |
|---|---|---|---|
| **A** | `blind` vs `tutor` | does rewriting beat merely measuring? | drops the gate we already run |
| **B** ⭐ | `rejecting` vs `rejecting + tutor` | **does the tutor earn its place on top of what's live?** | none — same gate both arms |
| **C** | 2×2 factorial | everything | 4 cells, ~2× the window; not a two-arm test |

**Recommendation: B.** The decision actually in front of us is *ship the tutor or not*, and B
measures exactly that increment. A re-asks a question the offline sample has already partly
answered (6/40 → 20/40 without the gate), and C is not what was asked for.

### 2.4 What B looks like operationally — and why it is a clean experiment

**The two arms differ in one field of one response.** Both refuse the same messages at the same
threshold with the same exemptions on the same slot schedule. The only difference:

| arm | what the 413 body carries |
|---|---|
| `rejecting` (control) | the refusal, as today |
| `rejecting_tutored` | the refusal **plus the tutor's rewrite** — "too long; here is the three-sentence-and-a-path version" |

A treatment that is one field wide is one you can attribute. It is also a better product either
way: tonight I had to rewrite my refused DM by hand, which is exactly the work the tutor exists
to do.

### 2.5 What it measures

| | |
|---|---|
| primary | share of refusals that produce a successful resend, and how fast |
| | length of the resend — does the rewrite get *used*, or just read? |
| secondary | abandoned messages · retry loops · total tokens per delivered DM |
| cost | tutor latency + tokens added to the refusal path |

### 2.6 The caveat this block inherits, and must print

The stopping rule has already been extended **twice, both times by someone who had seen the
interim numbers** (`generate_schedule.py:88-96`). A third block does not repeat that cost, it
compounds it. So: **fix the end date before the first slot opens, report blocks separately as
well as pooled, and say so wherever a p-value appears.** That is the existing rule, carried
forward, not a new one.

### 2.7 Order and dependencies

| step | blocked on |
|---|---|
| 1. Mr Radio's `dm_tutor` agent lands + the ~200-sample document | his run, and his gate with Rick |
| 2. **Rick reads the document and approves rewrite quality** | step 1 |
| 3. Wire the tutor into the 413 refusal path behind the arm flag | step 2 |
| 4. Generate the new block (new id, fixed end, ≥ Sat 08-15 14:00) | step 3 |
| 5. Run, then report | step 4 |

**Step 2 is a hard gate, not a formality.** Putting a rewriter into live traffic before approving
what it writes would ship unread text to real colleagues.
