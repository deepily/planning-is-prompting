## 1. Sibling vs. gitignored subdirectory

Rick's challenge — *"why isn't gitignore enough?"* — is correct for most of the case. **Four of the five arguments for moving out are fully answered by an ignore line**, and are retracted:

| Concern | gitignore fixes it? |
|---|---|
| Clutters `git status` | ✅ yes |
| Caught by `git add .` / `-A` | ✅ yes |
| Committed by accident | ✅ yes |
| Doc-viewer scope leak | ✅ yes (via `.docview.yml`) |
| **Deleted by `git clean -xdf`** | ❌ **no — the ignore entry is the kill list** |
| **Shared across worktrees** | ❌ **no — gitignore cannot merge two directory trees** — but see §3.3 |

### 1.1 `git clean -xdf`

`-x` is documented as *"do not use the standard ignore rules… remove ignored files as well."* The more carefully the data directory is gitignored, the more certainly a routine "reset this checkout to pristine" wipes it. A path outside the repo is unreachable by `clean` at any flag combination.

### 1.2 Worktrees

A worktree is a **physically separate directory tree**. gitignore governs what git *tracks*; it has no opinion on which directory a Python process opens.

**MEASURED** — Lupin has four live worktrees nested inside the repo, and the runtime files are unevenly spread across them:

| Tree | `.heartbeat-hold-*` | `.dm-inbox-hwm-*` |
|---|---|---|
| `lupin` (main) | 3 | 439 |
| `.claude/worktrees/cheech-orphan-bridge` | **1** | 0 |
| `.claude/worktrees/cheech-focus-bar-fix` | 0 | 0 |
| `.claude/worktrees/clayton-9fe8b80f-unit-collection` | 0 | 0 |
| `.claude/worktrees/rio-d8807dca-replica-state-analysis` | 0 | 0 |

Both families are keyed by **session id**, not by tree. A session in a worktree that reads its own private high-water mark would re-surface DMs the main checkout already consumed.

**Caveat, stated plainly**: with no worktrees in play, a gitignored subdirectory is fine and cheaper. The worktree fleet is what makes it wrong here — **and whether it is wrong at all is exactly what §3.3 puts back to Rick.**

## 3. Repo identity — the predicate, and the ruling that governs it

Option C only carries the fleet-global property **if repo identity is resolved correctly**. Two candidate predicates, and they disagree exactly where it matters:

| Predicate | From main checkout | From a worktree |
|---|---|---|
| `realpath` / `--show-toplevel` | `lupin` | `cheech-orphan-bridge` |
| `git rev-parse --git-common-dir` → parent basename | `lupin` | `lupin` |

**VERIFIED**, executed from inside `lupin/.claude/worktrees/cheech-orphan-bridge`:

```
--show-toplevel:   /…/lupin/.claude/worktrees/cheech-orphan-bridge
--git-common-dir:  /…/lupin/.git          → parent basename = "lupin"
```

⚠️ **Implementation note**: pass `--path-format=absolute`. Without it, `--git-common-dir` returns the bare relative string `.git` from a main checkout, and `dirname` of that is `.`.

### 3.1 🔴 `--git-common-dir` was already refuted and withdrawn — 2026-07-16

Mr Radio handed me this predicate, then caught that **Rick had already ruled against it** and stopped me before I codified it. `fleet_arbiter_loop.py:334-342`, verbatim:

> *"DEDUPE IS ON RESOLVED REALPATH, NOT ON `git --git-common-dir` (ruled 2026-07-16 after the git-common-dir instruction was refuted and withdrawn). git-common-dir is the identity of a REPO, not of a TREE: a worktree and its main repo SHARE one while being different directories holding different files, so deduping on it would silently DROP a worktree root — and a hold lives in a worktree today (lupin/.claude/worktrees/cheech-orphan-bridge). It also returns a RELATIVE path (".git"), which naively compared collides every repo into a single identity."*

The ruling's factual premise is **currently true, not merely historically true** — measured 2026-07-26, `cheech-orphan-bridge` holds exactly 1 `.heartbeat-hold-*` file **right now** (§1.2 census). This is the difference between *"Rick ruled on a situation that has since changed"* and *"Rick ruled on a situation that still holds"* — it is the latter, and that is why §3.3 is a question rather than a footnote. And the relative-path caveat is the same one I hit on my first run, i.e. the ruling was right about the implementation.

**The predicate survives only if we say which question it answers:**

| Question | Predicate |
|---|---|
| Which **trees** do I *sweep* for files that exist today? | **realpath** — each tree holds its own files; `--git-common-dir` would silently drop a worktree root |
| Which directory does a session *write* to? | **repo identity** — that *is* the fleet-global property |

### 3.2 🔴 Why the projects tree, not user-home

Mr Radio initially proposed `~/.claude/fleet-data/<repo>/`, citing `heartbeat_events.py:61` — `FLEET_EVENTS_DIR = ~/.claude/heartbeat-events`, **829 files** — as evidence that fleet-global "works: nothing has broken." `~/.claude` holds **23** runtime directories, including `mementos/`, `mementos-snapshot/`, `tasks/`, `sessions/`; mementos already have two homes (`~/.claude/mementos/` *and* `.claude-memento.md` at the repo root).

**Measured against the backup, that evidence reads the other way:**

- `sync-to-backup.sh:21` — `SOURCE_DIR` is a hardcoded absolute path to the **lupin repo root**. `rsync-exclude.txt` (99 lines) matches no runtime dotfile.
- ⇒ **442 runtime dotfiles are copied to DATA02 on every run today** (Mr Radio, `rsync -avn`).
- ⇒ 🔴 **`~/.claude/heartbeat-events` — all 829 files — is backed up by nothing.** Neither is `~/.claude/mementos/`.

So the existing user-home precedent is not a demonstration that fleet-global is safe; it is a relocation that shipped **without the backup half**, a year ago, whose loss mode is silent by construction — a break would not have announced itself. A null was being read as evidence without proving the instrument.

⇒ `DEEPILY_DATA_DIR` on DATA01 keeps the data on the filesystem the backup already targets; backup scope becomes **one path added to an rsync line**. `~/.claude/fleet-data` is dropped, and Rick's `DEEPILY_PROJECTS_DIR` analogy independently lands the same way.

## 4. The resolver contract

### 4.1 🔴 Read the variable directly — never recompute it

**MEASURED in two independent shells** (María's session and Mr Radio's), 2026-07-26:

| Variable | State |
|---|---|
| `LUPIN_ROOT` | **set** |
| `PLANNING_IS_PROMPTING_ROOT` | **set** |
| `DEEPILY_PROJECTS_DIR` | 🔴 **UNSET** |

The *derived* variable is present; the *parent it is derived from* — the line directly above it in the same `.bashrc` — is not. A long-lived session carries the environment snapshot from whenever it booted.

**And the failure is not a crash.** Mr Radio's sharpening:

```
"${DEEPILY_PROJECTS_DIR}/lupin-data"   ->   "/lupin-data"
```

An **absolute path at the filesystem root** — not empty, not an error, a plausible-looking path that `mkdir -p` would happily create.

⇒ **Rule**: resolve `DEEPILY_DATA_DIR` by reading `DEEPILY_DATA_DIR`. Never as `$DEEPILY_PROJECTS_DIR/<something>` — **because the failure mode is a valid path, not an exception.**

### 4.2 🔴 Fail loud when unset

A silent fallback to the repo root would recreate the exact clutter being removed — and would do it **only in long-lived sessions**, the ones nobody is watching.

⇒ **Rule**: unset `DEEPILY_DATA_DIR` **raises**. It does not return a plausible path.

This is the A0 shape from the arbiter janitor work: **omission must land on the safe state**, and here the safe state is *refuse*, not *write somewhere reasonable*.

### 4.3 Bootstrap

A fresh clone has no data directory. Creation is explicit — `mkdir -p "$DEEPILY_DATA_DIR/<repo>"` at first use — and never implicit-with-fallback.

## 5. 🔴 Backup coupling — a hard requirement, not a nice-to-have

Mr Radio's finding, adopted verbatim:

> The 3 `.heartbeat-hold-*` files carry hand-written `note_to_my_successor` text. They are backed up **today solely because they sit inside the repo.** Move them and they silently stop being backed up — irreplaceable, no alarm.

⇒ **The backup-scope change lands in the SAME commit as the relocation.** A location nobody backs up is strictly worse than a tracked subdirectory.

#### ⚠️ What the backup actually protects — both of us overstated it

**MEASURED**: `rsync-backup.sh:148-149` and `sync-to-backup.sh:69-70` both run `rsync -avh --delete`. **No `--backup`, no `--suffix`, no versioning.**

⇒ **It is a MIRROR, not an archive.** The janitor deletes a hold file; the next backup run deletes DATA02's copy too. The backup protects against **losing the disk** — it does **not** protect against **wrongful deletion**, which is the failure mode this entire design is about.

⇒ That trims the stated value of the coverage requirement. Mr Radio's original argument — *"the 3 cargo-bearing holds are backed up today solely because they live in the repo"* — is true, but what they are covered by was never protection against the janitor eating them.

**Nothing schedules it** — measured: no crontab entry, no systemd timer (only `dpkg-db-backup.timer`). The script is operator-run, `--write`, dry-run by default.

##### ⚠️ How often it actually runs — and why the obvious instrument gives the wrong answer

⚠️ **`rsync -a` PRESERVES mtimes**, so a file's mtime on DATA02 is the **source's edit time**, not the time it was mirrored. Verified:

```
README.md   DATA01 mtime 2026-06-18 09:13:49   DATA02 mtime 2026-06-18 09:13:49   ← identical
README.md                                       DATA02 ctime 2026-06-23 21:43:29   ← the write
```

⇒ An mtime histogram on the mirror measures **when files were edited**, not when the backup ran. **ctime** — inode change time, not preserved by rsync — is the instrument that dates the writes.

**MEASURED by ctime**, distinct days the mirror was written in July:

```
01 03 06 07 08 11 12 14 15 16 17 20 21 22 23 24 25
```

⇒ **17 of 25 days, not daily.** Gaps at 07-02, 04–05, 09–10, 13, 18–19, and today. Last write **2026-07-25 23:10**; nothing today.

*(Same data, two framings, both correct: **17 of 26 July days**, or **11 of the last 14** — 07-12 through 07-25, gaps at 13, 18, 19. Quoted here as the July window.)*

⚠️ **Honest limit on this instrument too**: a run in which nothing changed writes nothing, so a day with no ctime means *"no files changed **or** no run"* — the histogram is a **lower bound on run days**, not a run log.

##### 🔴 The reason both instruments were guesses: nothing records that a backup ran

**MEASURED**: neither `sync-to-backup.sh` nor the canonical `rsync-backup.sh` contains a `tee`, a redirect, or a `logger` call. There is no backup log in `/var/log` or in home. rsync's output goes to a terminal that scrolls away.

⇒ **No artifact answers the question**, which is why both of us were reduced to inferring from filesystem side-effects — and why one of those inferences was wrong and the other is only a lower bound.

⇒ **This reaches the precondition directly.** §5.1.1 specs the receipt as a dry run showing the data root in scope. That proves coverage **once, at the moment someone looks.** Nothing proves it kept happening. After the move, *"the data is backed up"* becomes a belief maintained by habit, with no artifact anyone can check — which is the same shape as §6.2's silent janitor, one layer out: **the thing that would tell you it stopped is the thing that doesn't exist.**

### ✅ 5.4 The completion stamp — RULED IN 2026-07-26

Rick, asked how completion would be measured after the dry run:

> *"Let's go ahead and include a timestamp plus status beside the destination."*

**The script writes a stamp itself, after rsync exits, recording that the run completed.** This is the logger named as a gap above; it is now in scope.

```bash
rsync -avh $DRY_RUN --delete --stats --exclude-from="$EXCLUDE_FILE" \
      "$SOURCE_DIR" "$DEST_DIR" | tee "$TMP_OUT"
rc=${PIPESTATUS[0]}

if [[ -z "$DRY_RUN" && $rc -eq 0 ]]; then
    { date -u +%Y-%m-%dT%H:%M:%SZ
      echo "exit=$rc"
      grep -E 'Number of (regular files transferred|deleted files)' "$TMP_OUT"
    } > "$STAMP"
fi
```

#### 🔴 It goes BESIDE the destination, never inside it

`--delete` removes anything in the destination that is not on the source — and the stamp exists **only** on the destination side. A stamp written into `DEST_DIR` is therefore deleted by the very next run.

**MEASURED** in a scratch tree rather than reasoned about:

```
stamp INSIDE  dst/  → after next run:  a.txt                   ← stamp GONE
stamp BESIDE  dst   → after next run:  dst  dst.last-backup    ← survives
```

⇒ `STAMP=/mnt/DATA02/…/projects-data.last-backup` — a **sibling** of the destination, not `…/projects-data/.last-backup`.

*(Note the recursion: the mechanism that erases the evidence of a wrongful delete is the same one that would erase the record proving the delete happened.)*

#### Why destination-side rather than a log on DATA01

A source-side log proves **the script ran**. A destination-side stamp proves **bytes reached DATA02** — and it survives the failure the backup exists for. If DATA01 is lost, the stamp is still there, stating how current the surviving copy is.

#### Contents

| Field | Answers |
|---|---|
| UTC timestamp | *"When did coverage last hold?"* |
| Exit code | **ran** vs **completed** — the distinction Rick's question was actually about |
| `--stats` transferred / deleted counts | *what it did*; a run that deleted 400 files is worth seeing |

#### What it converts

The stamp makes staleness **queryable** instead of believed:

```bash
find "$STAMP" -mmin +1440     # any output ⇒ no successful backup in 24h
```

⇒ §5.1.1's dry-run receipt proves coverage **once**. The stamp proves it **kept happening**, and anything can read it — a heartbeat check, a session-start line, or a person.

#### Two rules built in

1. **Stamp only on success.** A stamp updated regardless of outcome is worse than none — it asserts a freshness that isn't there.
2. **Exit 24** (*"some files vanished during transfer"*) is common and benign on a live tree. Stamp it, but **record the code**, so it is visible rather than silently folded into success.

⇒ Roughly six lines, and they belong in the **canonical template** so every instantiation inherits the stamp rather than each one re-deciding.

| Claim | Status |
|---|---|
| Protects against disk failure | ✅ yes |
| Protects against wrongful deletion | ❌ **no** — the delete mirrors |
| Window before a wrongful delete propagates | **roughly a day, sometimes two or three** — sustained by operator habit, enforced by nothing |

⇒ Three consequences worth carrying:
1. **Regularity is not a safety margin — it consumes the margin.** A mirror run reliably propagates a wrongful delete reliably. An *erratic* backup might accidentally preserve a deleted file for a week; a diligent one closes the only recovery window that exists. The habit that is normally a virtue is what destroys the surviving copy.
2. **The operator who runs the backup after a wrongful delete completes the loss**, unknowingly.
3. **"It's in the script" is not coverage** when nothing runs the script on a schedule — which independently strengthens §5.1.1's *receipt, not edit* rule: the dry run is the one moment anyone confirms the mechanism runs at all.

⇒ **And it closes the escape hatch.** *"Someone might notice before the next run"* needs the notice to arrive within about a day. Nobody notices a missing `note_to_my_successor` in a day — you notice when you go looking for it, which is weeks later, by which point both copies are gone.

⇒ **Not proposing versioned snapshots.** That is a new capability and Rick's call, out of scope for this row. Named here so the doc does not imply a protection that does not exist. The precondition stands; its stated value is **disk-failure coverage plus an unbounded-but-unmanaged window**, nothing more.

⇒ **Tightened**: that commit also carries a test that fails if the resolved data root falls outside backup scope. A rule in a commit message decays; a red test does not — §3.2 is what happens when the coupling is left to discipline.

### 5.1 The three tests (Mr Radio's, specified with controls)

**1 · `test_the_sweep_roots_CONTAIN_the_data_root`** — ranked first (§6.2). Resolve `DEEPILY_DATA_DIR`, call `_compute_hold_roots`, assert the sweep's roots contain **that one path**.
Controls: data root absent from the union ⇒ RED · a repo-only union ⇒ RED · **and the discriminator that matters** — a sweep over roots that exclude the data dir must report `files_seen 0` **while files genuinely exist**, so the test proves the *silent* case is detectable and not merely the loud one.

⚠️ **Asymmetry the test must encode** (Mr Radio, post-ruling): fleet-global means **one data dir per repo, not one per tree** — so the *data* side of the sweep is a **single derived path**, while the *repo* side stays a union of N trees precisely because each tree holds its own files. ⇒ Extra control: **adding a worktree must NOT add a second data root.** If it does, fleet-global didn't land, and the symptom is per-tree bookmarks again with everything still reporting green.

**2 · Fail-loud resolver** — `DEEPILY_DATA_DIR` unset ⇒ raises, never returns a path.
Controls: unset ⇒ RED · set-but-empty ⇒ RED · set-but-relative ⇒ RED (else `/lupin-data` is recreated by another route).

**3 · Backup-scope comparator** — resolve the data root exactly as production does; parse `SOURCE_DIR` from `sync-to-backup.sh` and every pattern from `rsync-exclude.txt`; assert the root is covered **and** matched by no exclude.
Controls: root outside backup scope ⇒ RED · root covered but matching an exclude line ⇒ RED · unparseable `SOURCE_DIR` ⇒ RED, never a silent pass.
This arm is the one that catches the *next* edit to `rsync-exclude.txt`.

**4 · Prefix-boundary guard** — assert `projects-data` never reads as inside `projects` (§5.2 trap).
Controls: naive `startswith(root)` ⇒ RED · guarded `startswith(root + os.sep)` ⇒ GREEN · exact-equality case still classified as inside.

⚠️ **Note on arm 3's assertion**: `SOURCE_DIR="/…/projects/lupin/"` — the backup targets the **lupin repo root**, not the projects tree. So the data root will **not** be under it wherever we put it; the backup script needs a second source (or a second invocation), and arm 3 asserts *covered by the backup*, not *under `SOURCE_DIR`*.

### 🔴 5.1.1 Backup coverage is a PRECONDITION on the move, not a co-commit

`$DEEPILY_DATA_DIR` **already exists on disk** (created 2026-07-26 17:45, empty) while `sync-to-backup.sh:21` still reads `SOURCE_DIR="/…/projects/lupin/"`. Nothing is at risk yet **because nothing has moved there** — but §5's requirement stops being a design note the moment the first file lands.

⇒ Mr Radio's sharpening, adopted: *"same commit"* is fine for the **code**; for the **data** it still leaves a window in which live files are uncovered. So:

**The backup source line must exist and cover `$DEEPILY_DATA_DIR` BEFORE the first `mv` — not in the same commit as it.**

⇒ And the precondition is discharged by a **receipt, not by the edit**: a dry run showing the data root in scope. A source line that has never been exercised is a claim, not coverage.

#### 🔴 "Add it to the backup" — the naive reading is the destructive one

`sync-to-backup.sh` is a **single SOURCE→DEST pair with `--delete` live** (`:69-72`):

```bash
rsync -avh $DRY_RUN --delete --stats --exclude-from="$EXCLUDE_FILE" "$SOURCE_DIR" "$DEST_DIR"
```

rsync accepts multiple sources, so **appending `projects-data/` as a second source would not error** — it would flatten the data dir into the *lupin* backup destination and then, with `--delete` armed, remove whatever in that destination no longer matches the merged set. The instruction "add the data dir to the backup" is destructive **against the backup itself** — the very thing the coverage exists to protect.

⇒ **The precondition is NOT "a source line exists in `sync-to-backup.sh`."** It is a **separate invocation with its own DEST**.

⇒ **And the convention for that already exists** — this needs no new mechanism. `planning-is-prompting/scripts/rsync-backup.sh` is the canonical template: *"copy to your project's `src/scripts/` and customize"*, with its own `SOURCE_DIR` / `DEST_DIR` / `EXCLUDE_FILE` and **dry-run by default** (`--write` to execute). Instantiate it for the data root; do not edit lupin's.

⇒ **`/mnt/DATA02/…/projects-data/` does not exist yet** — only `…/projects/`. The destination is part of the precondition, not an afterthought — **and its shape is unverified, not just its existence.** rsync would create it, but with what ownership and mode? DATA02 is a separate filesystem and the hold files are uid-sensitive. The receipt should show the **created directory**, not only the file list.

⚠️ **Write a fresh exclude file; do not inherit lupin's** — and the reason matters, because the obvious one is false.

**MEASURED**: `rsync-exclude.txt` (99 lines) contains **no pattern matching any runtime dotfile**. Its dotfile entries are `.git/`, `.venv/`, `.vscode/`, `.pytest_cache/` and similar; there is no `*.json` and nothing matching `.dm-inbox-hwm-*`, `.heartbeat-hold-*`, `.claude-memento*`, or `bug-fix-queue.md`. This is consistent with the earlier `rsync -avn`: **442 runtime dotfiles would be copied under that file.**

⇒ So inheriting it today would **not drop** the bookmarks. It would copy them.

⇒ **The honest reason to write a fresh file**: those 99 patterns were reasoned about against a *source tree* and none against a *data tree*, so today's coverage is **accidental rather than intended** — and an accidental property drifts the first time someone adds a source-tree pattern without knowing a data tree also reads that file.

⇒ Recorded this way deliberately. *"The old file would drop your data"* is falsifiable in one grep; someone will test it, find it false, and discount the recommendation along with the reason. *"The old file's coverage is unreasoned"* survives that test, because it is what is actually wrong.

⇒ **This is the argument for "receipt, not edit."** A dry run against a wrongly-merged second source would show lupin backup files queued for **deletion** — loud, immediate, and before anything is destroyed. The receipt is not a formality confirming success; it is the control that catches the wrong way of adding coverage.

### 6.2 🔴 The arbiter — the smallest change with the largest blast radius, and the only one that fails without a symptom

`_compute_hold_roots` unions three sources: `host_root` (`cu.get_project_root()`), the container-path registry translated to host paths, and `_scan_parent_for_repo_roots( Path( host_root ).parent )`, deduped on realpath.

**All three yield REPO roots.** The scan's predicate is a `.git` marker — `found.append( child )` fires only on a directory containing `.git`, and descent stops at a repo. Mr Radio proved it rather than read it:

```
parent/  a-repo/.git   +  lupin-data/   (no .git)
_scan_parent_for_repo_roots(parent) -> ['a-repo']
data dir seen? False
```

⇒ **`DEEPILY_DATA_DIR` is invisible to the root computation by construction.** Post-relocation the janitors sweep the repo roots — which no longer hold any runtime files — find zero, and stop.

**🔴 The failure shape is the worst available one.** `roots_swept` stays non-empty (the repos still exist), so `fleet_arbiter_hwm_report_no_roots` **does not fire**. The report reads *"roots swept 3, files seen 0, prunable 0"* — indistinguishable from a clean fleet with nothing to reclaim. And `enable_hold_deletion` defaults **True** at the production call site, so the **hold** janitor would stop reclaiming too: no error, no alarm, just quietly nothing, forever.

That is the same no-op shape killed in `11461241` — *sweep everything, keep everything, report green* — re-entering through a different door.

⇒ **Requirement, not a derivation**: the data root is **added to `_compute_hold_roots`' output as its own explicit source**, with test 1 (§5.1) asserting membership. Resolving the root correctly elsewhere is worth nothing if the sweep never receives it.

#### ⚖️ Sizing — corrected, because an earlier draft of this section inflated it

An earlier revision called this *"the biggest piece of work in the whole change"* and said it *"requires new logic rather than a changed path."* **Both overstated**, on Mr Radio's say-so and corrected by him after Rick pushed back:

`_compute_hold_roots` already builds a candidate list and dedupes it. Adding the data root is **one more `candidates.append()`** plus a resolver that reads `DEEPILY_DATA_DIR` and fails loud — **roughly five lines and a test.**

**What is actually distinctive about it is the failure mode, not the size:**

| Step | Wrong ⇒ |
|---|---|
| Resolver | files land in the wrong place — **visible** |
| gitignore | files appear in `git status` — **visible** |
| Backup | the dry-run receipt shows it — **visible** |
| **Arbiter roots** | **`roots 3 · files 0 · prunable 0` — reads as a clean fleet** |

⇒ **The test exists because the failure is quiet, not because the work is hard.** Every mechanical finding above — the `.git` predicate, the no-roots alarm not firing, `enable_hold_deletion` defaulting True underneath — is measured and stands unchanged. Only the sizing was wrong.

⇒ Recorded rather than quietly amended: a document that calls a five-line change *"the biggest piece of work"* gets discounted wholesale the first time a reader opens the function and finds a list append. **The finding is strong enough that it must not be carried by a sizing claim that won't survive contact** — the same failure shape as the exclude-file justification in §5.1.1: right recommendation, invented reason, and the reason is what gets tested.

### 6.2.1 ❌ REJECTED: riding the `external repos` registry

**The shortcut**: `_registry_container_paths` reads `external repos` + `external repo <name> path` and returns the strings with **no `.git` validation and no repo-ness check** (`fleet_arbiter_loop.py:170,175`). Register the data dir there and `_compute_hold_roots` picks it up — a config change instead of a code change.

**Why it's rejected**: the doc viewer reads **the same keys** — `_scope_registry.py:294, 307, 317`. Registering `DEEPILY_DATA_DIR` there would publish the fleet's runtime state as a browsable doc-viewer scope: DM bookmarks, and hold files with hand-written successor notes, served over the web UI. One registry, two consumers, one of them a public read surface.

**⚠️ And it would test clean.** `_scope_registry.py:311-313` *skips* any scope whose path doesn't resolve in the viewer's runtime — so with the data root outside the container's mounts (§5.2), the shortcut would look correct and safe: arbiter picks it up, doc viewer silently declines, a warning scrolls past in a log nobody reads. A later bind-mount would arm the publish with no config change, no code change, no alarm.

Recorded here **as rejected, with its reason**, because the "no validation" fact is genuinely inviting and the next person will find it and reasonably conclude the shortcut is supported. A rejected option with its reason is cheaper than the same investigation run twice.
