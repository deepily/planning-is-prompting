# Cross-repo parity: the substitution block is one paragraph, not a templating problem

**Date**: 2026-09-01 · **Author**: María 🌸 (`3396ba14`) · **Status**: ✅ **BUILT** 2026-09-01 — the rule below is implemented and tested; the open items in §"What this does NOT settle" remain open
**Seed**: `8a84018` (recorded the blocker) · **Retro**: `io/post-games/2026.09.01-parity-blindness-and-the-tidy-generalization-post-game.md`

---

## The problem, in one line

`doc_deploy_parity.py` compares a canonical doc against a deployed copy. On the `~/.claude` axis
that works. On a **cross-repo** axis — this repo's `.claude/` against lupin's `.claude/` — a
**correctly installed** copy reports as DRIFTED, because an installed command is *supposed* to
carry a different project prefix, and the tool sees only "a paragraph that stopped being
identical."

Adding cross-repo pairs today therefore buys **one permanently red paragraph per pair**, clearable
only by a `KNOWN_DRIFT` entry that can never self-prune — which is exactly the *"list of things
nobody decided"* the allow-list was designed to prevent.

## What I assumed, and what the measurement says

I recorded this in TODO.md as *"needs per-pair substitution handling"* — which sounds like a
templating engine, a per-pair config file, and a design decision worth a meeting.

**Measured across all four shared pairs (2026-09-01, after Mr Radio's syncs):**

| pair | drifted | only-canonical | only-deployed |
|---|---|---|---|
| `plan-decide` | **1** | 1 | 1 |
| `plan-post-game` | **1** | 0 | 0 |
| `spin-up-swe-team` | 0 | 0 | 4 |
| `guided-decision-walkthrough` | 0 | 0 | 0 |

**Both drifted paragraphs are the same paragraph**, structurally — the project-configuration
block, identified by the literal marker `**[SHORT_PROJECT_PREFIX]**`:

```
C: 2. **MUST use project configuration**: - **[SHORT_PROJECT_PREFIX]**: [PLAN]  - **Working directory**: …
D: 2. **MUST use project configuration**: - **[SHORT_PROJECT_PREFIX]**: [LUPIN] - **Working directory**: …

C: - **[SHORT_PROJECT_PREFIX]**: [PLAN]  - **Canonical workflow**: planning-is-prompting → …
D: - **[SHORT_PROJECT_PREFIX]**: [LUPIN] - **Canonical workflow**: planning-is-prompting → …
```

⇒ **There is no general substitution problem. There is one conventional block**, already named by
this repo's own `CLAUDE.md` (*"Local configs should define the `[SHORT_PROJECT_PREFIX]`"*), and the
installer already writes it. The expensive design I recorded was a guess about a class of cases;
the measured class has exactly one member.

## Proposed rule

**A paragraph containing the literal token `[SHORT_PROJECT_PREFIX]` is a project-configuration
block, and is compared for SHAPE rather than TEXT.** Same keys present, in the same order ⇒ the
copies agree. A key added, removed, or renamed ⇒ real drift, reported normally.

Why shape and not exemption: a blanket exemption would hide a *genuine* defect — a deployed copy
that lost the "Working directory" line entirely, or gained a key canonical never had. The whole
argument for the anchor rule (§`MIN_ANCHOR_CHARS`) applies here too: identity should be anchored
on something that survives the legitimate edit, and the legitimate edit here is **the value**, not
**the key**.

### Sketch

```python
# A paragraph carrying this token is written by the installer, per repo. Its VALUES are supposed
# to differ; its KEYS are not.
SUBSTITUTION_MARKER = "[SHORT_PROJECT_PREFIX]"

def config_block_keys( normalized ):
    """The bolded key names in a project-configuration paragraph, in order."""
    return re.findall( r"\*\*([^*]+)\*\*:", normalized )
```

In `same_paragraph`, when **both** blocks carry the marker: agree iff `config_block_keys` match.
Report as drift with reason `"config-keys"` when they do not — a distinct reason string, so the
report says *which* kind of disagreement it found rather than flattening it into "similarity".

## What this does NOT settle

1. **Portability.** The pairs themselves still must not hardcode a sibling checkout. This spec
   makes cross-repo comparison *meaningful*; it does not decide where the pair list comes from.
   An env-var-rooted or config-file pair source is a separate question, still open.
2. ~~**`plan-decide` has `only_c=1, only_d=1`** — not examined.~~ **EXAMINED 2026-09-01, and it
   is a SECOND per-repo block:**

   ```
   only in canonical: **Project**: planning-is-prompting (meta-repository) **Version**: 1.0…
   only in deployed:  **Project**: lupin (installed from planning-is-prompting) **Version**: 1.0…
   ```

   Also legitimate installed-copy customization — but it carries **no `[SHORT_PROJECT_PREFIX]`
   token**, so the rule above does not see it. The two copies are dissimilar enough not to pair at
   all, so each lands in `only_canonical` / `only_deployed`, which are verbose-only and **do not
   ring**. ⇒ **No false positive, and no guard either**: if this block ever lost a key, it would
   stay quietly unpaired and nothing would report it.

   **Deliberately not fixed here.** Recognising it needs a different signal — its opening `**Project**:`
   is too generic to key on — and inventing one now would be exactly the guess this document was
   written to correct. Recorded as the known edge, for whoever has a real second case to measure
   against.
3. **The marker is a convention, and conventions rot.** If a future installed copy omits the
   token, its config block silently becomes an ordinary paragraph and rings as drift. A guard
   asserting every installed copy carries the marker would catch that, and is not written.
4. **Measured on two repos.** Every other repo in the fleet carries its own copies and none were
   read.

## Cost

Small. One constant, one helper, one branch in `same_paragraph`, and a test that a config block
differing only in its VALUE is not drift while one differing in its KEYS is. It does not need a
worker; it needs an hour and the decision in the "Proposed rule" section above.
