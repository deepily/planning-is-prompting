## 3. The design question this plan must answer FIRST

**A naive check 2 is a false-positive machine.** `0.5` appears in arithmetic, in fixtures, in unrelated ratios. A guard that fires on every literal equal to a registry value will be disarmed within a week — and a disarmed guard is the "guard someone will trust" defect this repo already has a name for.

So the plan is **not** "grep for the value." Three candidate scopings, narrowest first:

| Option | Rule | False-positive risk | Verdict |
|---|---|---|---|
| **A (RECOMMENDED)** | Fire only on a literal inside an `ast.Compare` — a **decision point** — where the compared value is one the registry declares | Low; targets the actual pathology | **Start here** |
| B | Fire on any literal equal to a registry value anywhere in product roots | High — arithmetic and fixtures | Rejected |
| C | Require every decision-point literal to carry an inline allow-marker | Low FP, but it is a convention, and a convention is a rule | Fallback only |

Option A keeps the check honest to its own wording: *at a decision point*, not *anywhere*.

**Precedent for the instrument**: an `ast` walk over product roots is the pattern already used in `test_rubric.py:288-299` and `test_runtime_gate_invariant.py:107-123` — the same instrument `4197a2b4` names as the one that can tell "the module exists" from "the capability is in the run." Reuse it; do not invent a third.

## 4. The tests-surface question — the live instance forces it

`test_overlap.py`'s `DF_THRESHOLD=0.5` is real drift, and it lives in the surface the guard deliberately excludes. **Excluding tests is defensible** — a test may legitimately pin a value to assert behavior AT it — **but it must be a stated exclusion with a reason, not an accident of the root list.**

⇒ Deliverable: EITHER (a) the exclusion is documented in the guard's docstring with the reason, and `test_overlap.py` is migrated to read the registry anyway; OR (b) tests are scanned under a relaxed rule. **Do not leave it as an unexplained gap** — the row's own thesis is that a mechanism nothing forces you to use is a rule with extra steps.

## 5. Acceptance criteria

1. CHECK 2 exists as a named test in `test_tunables_guard.py`, discoverable by the same convention as checks 1/1b.
2. **Negative-controlled in BOTH directions**, matching check 1b's standard exactly: it FIRES on a planted use-site literal at a decision point, and does NOT fire on correct registry access. A check that only ever passes is not evidence.
3. It catches the **known live instance** (`test_overlap.py` `DF_THRESHOLD=0.5`) — or explicitly documents why that surface is excluded. One or the other, never silence.
4. **Per-root vacuity floor**, as check 1 already has, so a path typo cannot silently disarm it.
5. The check reads the registry at **access time** — it must not itself snapshot at import, which is the trap check 1b exists for. **A guard committing the defect it guards is this repo's most-repeated failure**; do not add another instance while closing one.
6. **A false-positive census is REPORTED**: run against the current tree and print the hit count AND the scanned-file count. **Zero hits on a tree with a known live instance means the check is broken, not clean.**
