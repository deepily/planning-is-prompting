## 4. Three defects found while doing the pass

1. **`abf845e2` and `05c5d4b7` are filed under project `lupin`** while their titles say
   `[LUPIN-MOBILE]` and their bodies point at `src/lupin-mobile/`. Any per-project roll-up
   counts them on the wrong side. Not corrected here — a project re-file is the owning
   manager's call, not a side effect of an epic pass.
2. **`48b5f19e` has no owner.** A queued row nobody owns is not owed work; it is a note.
3. **The MCP verb and the REST route spell the parked switch differently, and the mismatch is
   silent.** The MCP tool takes `include_parked=True`. The route
   (`src/cosa/rest/routers/tasks.py:1130`) takes **`hide_parked`, default `True`** — there is no
   `include_parked` parameter, so FastAPI drops the unknown query param and answers as though you
   had never asked. Separately, `limit` is honoured but **not the only bound**: a `char_budget`
   cuts the page below it, which is why `limit=500` came back with 15 rows beside
   `total 2174 / has_more true`. Neither behaviour is a bug in the route; together they mean an
   audit written against the MCP verb's vocabulary and run over HTTP describes eleven rows and
   calls it eighteen — silently, and with a plausible-looking total sitting right next to it.

That third one is the same defect the prior art warned about, arriving through a different door.

> **Corrected 2026-08-29, an hour after first publication.** This entry first read *"the endpoint
> silently ignores `include_parked` and caps `limit`."* Both halves were wrong in the same
> direction — I inferred the route's contract from the MCP tool's parameter names instead of
> reading `query_tasks`, and named the endpoint as the faulty party. The defect is real and is a
> **naming mismatch between two surfaces**, which is a different fix from "the endpoint is
> broken." Reading the signature took two minutes and I did it only after being asked something
> else entirely.

## 5. The board is a rendered page, not a document — and I did not check that first

Rick asked, right after this pass, whether he would *"see clearly and plainly"* that he is a
blocker. I answered **no** from the store's data model and the 2026-08-18 design doc. **That was
wrong.** A UI had been built on top of the field since, and it already answers his question:

| | |
|---|---|
| `notifications.js` | `EPIC_ON_RICK_KEY` — a sentinel group rendered **first**, above every epic |
| Section title | **⏳ Waiting on Rick**, subtitled *"Highlighted, not moved"* — rows also stay in their epic |
| Matcher | `_taskWaitsOnRick` — any `blocked_by` ref with id `rick`, case- and space-insensitive, **kind deliberately ignored** so a row assigned his name counts the same as a gate raised on him |

**Two gaps survive, and the second is mine:**

1. **The section vanishes at zero.** `renderEpicBoardTable` guards it with
   `if ( model.onRick.length > 0 )`. The Drift group in the same function renders its empty state
   as **"✅ No drift"**, and its own comment says why: *"A section that vanishes when it is
   satisfied cannot be distinguished from a section that failed to render."* That reasoning was
   never applied to the Rick section. His count is zero tonight, so he opens the board and sees
   nothing where the answer should be.
2. **The epics I minted had no stories.** `src/conf/epic-stories.json` is the hand-maintained map
   the page reads, and §4.4 of the prior art says the manager who mints an epic writes its line
   **in the same turn**. I minted three and wrote none, so `coverage-100-mandate`,
   `quick-ask-ship` and `park-reason-fidelity` would have rendered as de-slugged keys with no
   story. Added; the file now holds 18 keys.

**The lesson is the night's own headline, turned on me**: I answered a question about a *rendered
surface* by reading the *data model*, which is a correct measurement of the wrong subject. Same
shape as the five instruments that misled me earlier in the evening.
