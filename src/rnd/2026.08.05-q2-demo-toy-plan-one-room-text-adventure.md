# Plan: "The Lockroom" — a one-room text adventure

**Date**: 2026.08.05
**Status**: Draft for review
**Size**: one room, one puzzle, one exit
**Target**: playable build in a single session

---

## What we're building

A text adventure with exactly one room. The player wakes in a locked storeroom and has to get
out. Everything is typed: the player writes what they want to do, the game writes back what
happened.

The room contains four things: a **door** (locked), a **desk** (has a drawer), a **key** (in the
drawer, under a folded cloth), and a **window** (painted shut, but it's a red herring — it never
opens).

The whole game is: look around → find the desk → open the drawer → move the cloth → take the
key → unlock the door. Six moves if you know them. Most players take twenty.

**Why this shape.** One room bounds the content problem to something we can finish, while still
needing every system a bigger game needs: input handling, world state, a description layer, and
a win condition. If the one-room version is good, the second room costs almost nothing.

---

## Scope

**In:**
- One room, four objects, one win condition
- Typed input, text output, runs in a terminal
- The player can look, move things, take things, open things, and use things
- The game remembers state within a session (drawer open, cloth moved, key held)

**Out:**
- Save/load between sessions
- More than one room
- Any combat, NPCs, or inventory limits
- Sound, graphics, a web UI

**Done when**: a person who has never seen the game can sit down, type into it, and get out of the
room without being told the answer.

---

## Design decision — how do we understand what the player typed?

This is the one real choice in the plan, and it shapes everything downstream.

### Option A — parse the words

A vocabulary table and a small grammar. We define the verbs we accept (`look`, `take`, `open`,
`move`, `unlock`, `use`), the nouns in the room (`door`, `desk`, `drawer`, `key`, `cloth`,
`window`), and a handful of sentence shapes (`VERB`, `VERB NOUN`, `VERB NOUN PREP NOUN`). Anything
that doesn't match gets a "I don't understand that" back.

- **Cheap and instant.** No network call, no cost per move, no latency.
- **Completely predictable.** The same input always does the same thing, which means we can test it
  exhaustively.
- **But it fails at the edges the player will actually hit.** "Look under the cloth" works;
  "peek beneath the rag" doesn't. Every synonym is a line of config someone has to think of in
  advance, and the player experiences each gap as the game being stupid.

### Option B — route intent through a model

Send the player's raw text to a model along with a description of what's in the room and what state
it's in. Ask it to return a structured action — verb plus target, from a fixed list we define. The
game engine then executes that action exactly as it would in Option A.

- **Handles the whole surface of English.** "Peek beneath the rag", "check under that cloth thing",
  and "move cloth" all land on the same action. The player stops fighting the parser.
- **The room description can stay in one place.** We describe the room once, in prose, and the model
  reads it — instead of maintaining a vocabulary table that has to stay in sync with the prose.
- **But we give up determinism.** The same sentence can route differently on two runs. That makes
  the game harder to test, and it introduces a failure mode Option A doesn't have: the model
  confidently returning a legal action the player didn't ask for.
- **And it costs something per move** — money and about a second of latency, on a game where the
  player types constantly.

### What I'd do

**Option B, with the action list locked down.** The model's only job is to map free text onto a
fixed, small set of actions the engine already knows how to run — it never invents an action, never
touches game state, and never writes the output text. If it returns something not on the list, we
fall back to "I don't understand that", exactly like Option A.

The reason isn't that B is more capable. It's that in a text adventure, *the parser is the entire
user interface*, and Option A's failures land on the player as the game being broken. Bounding the
model to a fixed action list gives us most of B's forgiveness while keeping A's blast radius.

Open question I don't have a good answer to: **how do we test a parser that isn't deterministic?**
A fixed set of phrasings with expected actions gets us a regression suite, but it can't tell us the
model won't misroute a phrasing nobody thought to write down.

## Build order

1. **The room, as data.** Four objects, their states (`drawer: open|closed`, `cloth: placed|moved`,
   `key: in_drawer|held`, `door: locked|open`), and the rules for what each action does to them.
   No input handling yet — drive it from a test.
2. **The output layer.** Given the room's state, write what the player sees. This is where the game
   is actually good or bad, and it's the part that has nothing to do with the decision above.
3. **The input layer.** Whichever option we pick. It produces an action; step 1 already knows how
   to run one.
4. **The win condition and the loop.** Tie it together, play it, fix what's boring.

Steps 1 and 2 don't depend on the parser decision at all, so they can start immediately either way.

---

## Risks

- **The red herring window is the thing most likely to make players quit.** If a player spends ten
  minutes on the window, that's a design failure, not a puzzle. We need the description to hint
  that it's painted shut *the first time they look*, not the third.
- **The cloth is a hidden step.** Nothing in the room says "look under things". If playtesters miss
  the key, the fix is in the desk's description, not in the puzzle.
- **Option B's latency lands on every single move**, including the ones where the player typed
  something trivial like "look". Worth checking whether obvious inputs can skip the model entirely.

---

## What I'm not sure about

- Whether one room is enough game to be worth playing, or whether it reads as a demo of a game.
- Whether the win condition should be the door at all — "get out" is the obvious goal, and obvious
  goals are the ones players stop reading the prose to chase.
